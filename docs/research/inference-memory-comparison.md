# SakuraTTS 相对原版的显存收益

日期：2026-09-20。设备：RTX 5060 8 GB，Windows WDDM，驱动 610.62。模型：Sakura V2ProPlus，日文、单请求。

当前可以支持的结论是：在相同的 84 次混合请求后，启用声学内存池回收的 SakuraTTS FP32，比原版 API FP16 少占 **398.5 MiB 空闲显存，降低 25.0%**；观测峰值低 **226.5 MiB，降低 9.9%**。与我们此前保留工作区的策略相比，这次默认回收又减少了 **1138.0 MiB 空闲显存，降低 48.7%**。

同为 FP32 的原版对照来自另一组 14 次请求：尚未默认启用回收的 SakuraTTS，观测峰值已低 **48.6%**。目前没有原版 FP32 的 84 次对照，不能把两组百分比相加，也不能把当前 1197 MiB 与另一组原版 FP32 的空闲值直接解释为同条件优化率。

## 相同精度：14 次请求

顺序为短句 3 次、长句 3 次、多句文本 3 次、短句 5 次，请求间隔 2 秒，末尾空闲 30 秒。此组 SakuraTTS 使用回收优化前的默认策略。三条路径全部请求成功。

| 路径 | 观测峰值 MiB | 结束后空闲 MiB |
|---|---:|---:|
| 原版 API FP32 | 3707.5 | 2917.5 |
| SakuraTTS FP32，保留工作区 | 1907.1 | 1907.1 |
| 原版 API FP16，供不同精度参考 | 2161.5 | 1621.5 |

与原版 FP32 相比，SakuraTTS 的峰值减少 **1800.5 MiB（1.76 GiB，48.6%）**，空闲减少 **1010.5 MiB（0.99 GiB，34.6%）**。这组比较说明原生推理链路在相同精度下已有显存收益，但也暴露了旧策略的问题：长句后的空闲占用，比原版 FP16 高约 285.5 MiB。

## 当前策略：84 次混合请求

每轮 28 次，包含短句、长句、扩展长句、多句文本及五种参考音频切换，共三轮，请求间隔 0.35 秒，最后空闲 30 秒。以下采用前次逐个启动服务、分别测量的结果；收缩策略与本次新默认值一致。

| 路径 | 观测峰值 MiB | 第 1 轮结束 MiB | 第 2 轮结束 MiB | 最终空闲 MiB |
|---|---:|---:|---:|---:|
| 原版 API FP16 | 2277.5 | 1597.5 | 1597.5 | 1595.5 |
| SakuraTTS FP32，旧保留策略 | 2335.1 | 2335.1 | 2335.1 | 2335.1 |
| SakuraTTS FP32，当前收缩策略 | 2051.1 | 1197.1 | 1197.1 | 1197.1 |

| 对照 | 峰值减少 | 空闲减少 |
|---|---:|---:|
| 当前策略相对原版 API FP16 | 226.5 MiB / 9.9% | 398.5 MiB / 25.0% |
| 当前策略相对我们的旧策略 | 284.0 MiB / 12.2% | 1138.0 MiB / 48.7% |

计算方法为 `(对照值 − 当前值) / 对照值`，使用原始未舍入数据计算，表中显示一位小数。当前约 **1.17 GiB** 的空闲占用，仍包含模型权重、GPT 状态、CUDA 上下文及其他常驻分配。

本次代码修改后，又在新旧策略上各跑了 84 次，三轮结束值分别稳定在 2335.1 与 1197.1 MiB，重复验证了回收效果。此次新服务与旧服务共存、逐个发请求，因此其峰值和耗时不用于替代前次分别运行服务的原版对照。两次都没有发现相同负载下逐轮累积增长；这仍不是数小时驻留验证。

## 显存省在哪里

SakuraTTS 日常推理使用原生 CUDA GPT 与 ORT 声学图。前端、参考编码和训练/导出依赖分开，日文路径沿用原版零 BERT 特征语义，主推理进程不加载中文 BERT 或完整 PyTorch 推理栈。GPT 的 Prefill 与 Decode 复用模型权重；声学图接收准备好的参考条件，不常驻原始参考编码网络。上述设计共同影响总占用，现有对照没有逐项拆出各自节约多少 MiB，不能把整体差额都归因于某一个模块。

本次增量优化的原因更明确：长输入会扩大 ORT 声学 arena，旧策略在请求完成后保留这些区域；新策略通过每次 ORT 执行的回收选项释放空闲区域。它保留权重与活跃分配，不重建声学 Session，不改变 FP32、采样规则或模型结构。这里的主要收益是降低请求后的常驻占用，不是为任意长输入设置峰值上限。

默认值由 `NVIDIAEngine` 统一提供，公共 Python、CLI 和 HTTP 复用。需要对照或优先复用工作区时，可通过 `experimental={"acoustic_arena_shrink": False}` 关闭；旧 `synthesize` 命令提供 `--no-acoustic-arena-shrink`。参见 [Python API](../python-api.md) 与 [HTTP API](../http-api.md)。

## 原版 WebUI 为什么高位不回落

另一次实验直接调用原版 WebUI 的模型加载和推理函数，保留 FP16 与默认 CUDA Graph，只省略 Gradio 界面。73 次调用后，用长句与逐步清理区分缓存来源：

| 操作 | WDDM 显存 MiB |
|---|---:|
| 长句完成，空闲 30 秒 | 2365.5 |
| 再执行 Python GC | 2365.5 |
| 再执行 `torch.cuda.empty_cache()` | 1989.5 |
| 再释放 Graph 并清理缓存 | 1763.5 |

空闲缓存占了其中至少 376.0 MiB。Graph 路径还额外保留约 148.0 MiB 的解码器参数、117.2 MiB 的固定 KV，以及图和工作区；这部分活跃分配不能只靠 `empty_cache()` 释放。三轮请求结束值没有单调增长，本次复现的是缓存与 Graph 常驻导致的高位保留。

WebUI 实验的请求序列、结束输入及入口与 API 不同，因此不计算它与 SakuraTTS 的严格节省比例；直接比较“2365.5 → 1197.1”会混入这些差异。本报告也没有覆盖 Gradio 队列和前端断连行为。

## 延迟、输出与验证

前次资源采样轮中，回收与保留策略的耗时中位数接近，差异约 −2.5% 至 −0.1%。本次另外停止显存采样，让两套已预热服务交替接受同一请求，每类各三次，得到：

| 输入 | 保留策略 ms | 回收策略 ms | 增量 |
|---|---:|---:|---:|
| 短句 | 359.0 | 386.4 | +27.4 ms / +7.6% |
| 长句 | 3606.2 | 3629.9 | +23.7 ms / +0.7% |
| 扩展长句 | 5435.7 | 5582.9 | +147.2 ms / +2.7% |
| 多句文本 | 1666.2 | 1708.1 | +41.9 ms / +2.5% |

两套服务共存带来的显存压力、桌面负载和较少的重复次数限制了计时结论。可以确认回收有显存收益，但不能承诺零延迟成本，也没有依据给出相对原版的统一加速倍数。

本次 84 对音频长度全部相同，PCM16 最大差为 1 个量化单位，最大全段 RMS 差为 0.01696 个量化单位；不逐字节相同。另测多片段模式 0/1，完整 PCM 长度一致、最大差 1 个量化单位。流式读取 2048 字节后断连，服务约 0.063 秒后恢复 ready，后续请求正常完成。该次断连不能代表所有中断时机。

提交前使用开发环境的 `python -m unittest discover -s tests -q` 执行 327 项测试，325 项通过、2 项跳过。另修正目录迁移后的一处测试导入路径，该文件单独执行的 7 项测试通过。`uv build --wheel` 成功构建分发包。尚未做本次听音/ASR 验收、数小时驻留、其他 GPU、其他语言或所有模型的验证。

## 测量口径与证据

数字统一来自 Windows PDH 的 GPU Process Memory / Dedicated Usage。SakuraTTS 取主进程与声学 worker 同一时刻之和；它是进程归属显存，跨进程共享分配可能重复计入，不能当作严格独占物理显存，也不能与整卡 `nvidia-smi` 或 PyTorch `allocated` 混用。采样间隔中位数约 20.8 ms，更短的尖峰可能漏采；这些结果不包含冷启动峰值。

原版与 SakuraTTS 使用同一组权重、参考音频和 HTTP 参数：日文、`seed=1234`、`top_k=15`、`top_p=1`、`temperature=1`、`repetition_penalty=1.35`、`cut0`、单项批次、非流式 WAV。但 NumPy 和 Torch 的随机序列不同，输出时长也不同。它们是同一应用请求的资源对照，不是相同 token 或逐帧音频的算法对照。

固定身份：GPT `dc0960f365affd723e096f03dc5d0fc37857e68ba30862754ff31caa9645fea4`，SoVITS `47f8d5d2c6d1a6e83d6225f0f83c3bc018b5910d7aa2d76aac3d6faaacce992d`；原版 `TTS.py` SHA-256 为 `83a849f2d0accc8a9d51e7ad1cb7475fa135eb7952de8dfae377ea95e5d85c09`。原版发行包没有可用 Git commit。

本机原始数据保存在以下目录，按项目约定不纳入 Git；本文保存经过核对的结论与口径，克隆仓库不会获得这些采样文件和音频：
