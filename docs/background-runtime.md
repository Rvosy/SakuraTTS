# 后台驻留与提前唤醒

状态：可选控制模式，2026-09-22。已提供显式启用的休眠、唤醒、保活和独立推理进程，并接入 H 极限档。本文说明实现边界及后续测量方向；调用方式见 [HTTP API](http-api.md)，必须保持的行为见 [推理契约](specs/inference-contract.md)。[首轮单机验证](../research/notes/managed-runtime-20260922.md)已覆盖真实模型的睡醒、进程树回收和 PCM 一致性，长期稳定性仍待验证。

[后续资源精简记录](../research/notes/managed-refinement-20260922.md)补充控制服务主存减负与 H 极限档的 HTTP 对照。RSS、私有提交和显存分别统计，不能把系统内存数字当作显存占用。

保留现有默认行为，新增显式启用的控制模式。本文后续的休眠启动、进程隔离、自动唤醒和空闲退出均属于控制模式，不作为现有服务的默认迁移方案。

## 使用目标

SakuraTTS 面向长时间后台运行、间歇生成语音的应用。桌宠是主要使用场景，也应能供聊天客户端、朗读工具和其他本地程序调用。TTS 不负责请求大模型，也不需要知道角色状态、聊天轮次或具体宿主。

在不改变现有默认行为的前提下，控制模式的优化优先级如下：

1. 长时间无请求时，释放 TTS 推理进程及其 GPU 上下文，保留可接受请求的控制服务。
2. 调用方预知即将需要语音时，可以提前唤醒，让加载与上游任务并行。
3. 连续对话期间复用已就绪的资源，避免每句话都承担进程冷启动成本。
4. 在音频行为不变的前提下降低活动时峰值显存、唤醒耗时和后台主存。

“待机资源接近零”需要分项定义：GPU 目标是没有存活的 TTS GPU 工作进程及其分配；CPU 目标是无请求时接近空闲；HTTP、解释器和少量配置仍占主存，不能承诺所有资源都为零。RSS 是进程驻留主存，私有提交也是主存指标，都不是显存。GPU Dedicated / Shared Usage 另行报告，不能将整张显卡的系统、桌面或其他应用占用归零作为验收要求。

## 默认模式与可选控制模式

| 行为 | 默认模式（保留现状） | 控制模式（显式启用） |
| --- | --- | --- |
| 启动 | 按现有配置创建 `Inference`、加载模型；未配置模型时沿用现有行为 | 读取配置后休眠，收到唤醒或合成请求才启动推理进程 |
| 推理所有权 | HTTP 进程内的专用线程，继续使用现有声学与前端 worker | 独立推理进程内的同一线程，控制进程管理整棵推理进程树 |
| 请求后资源 | 遵循用户已选的执行档位，不新增空闲退出 | 同样遵循执行档位，并按保活和空闲期限退出推理进程 |
| 提前唤醒与休眠 | 不启用新的生命周期接口和定时器 | 提供 `wake`、`sleep`、状态查询与请求自动唤醒 |
| 现有调用方 | 启动命令、配置和请求方式继续有效 | 显式选择模式后仍使用原有 `/tts` 参数 |

模式在启动时通过 `--runtime-mode direct|managed` 确定，省略时为 `direct`。CLI、Python 服务入口及整合包启动器只有显式选择 `managed` 后才进入控制模式，不根据调用方、机器显存、推理档位或空闲时长自动切换。

```powershell
.\start-server.bat -c configs/tts_infer.yaml --runtime-mode managed --idle-sleep-seconds 60
```

空闲超时默认 60 秒，唤醒准备超时默认 120 秒，工作进程操作超时默认 300 秒；对应选项为 `--idle-sleep-seconds`、`--wake-timeout-seconds` 和 `--operation-timeout-seconds`。它们都是有限正数，普通默认模式不使用这些计时器。

不传新选项时，保留当前启动加载时机、默认 FP32、现有实验配置含义、并发 409 约束、流式背压、断连取消和模型切换行为。原来启动时发现的配置或加载错误仍在启动时报出，不推迟到第一条语音请求。默认模式的 `/health` 响应结构与含义不变，新的资源状态由控制模式的 `/runtime` 表达。控制模式未启用时，不注册新增的 `/runtime` 路由，访问仍按不存在的接口返回 404。原有 `/control` 的退出与重启用途保持不变。

两种模式共用 `Inference`、模型校验、参考准备、采样和音频生成代码。控制模式增加进程生命周期和传输层；默认模式继续直接调用原有引擎，不要求为它额外启动完整推理进程，也不复制一套推理实现。现有进程内 `Engine` 的默认生命周期不变。

## 可以共用的优化

能保持现有功能、生命周期和输出约束的优化，经测量与回归后可以进入两种模式，例如消除重复临时数组、减少不必要复制、修复异常路径的资源残留、优化模型解码和上传。复用校验或参考缓存时，仍需验证模型、文件和精度身份，不能跳过必要的失效检查。

是否纳入默认路径取决于实际代价。保留额外 CPU 权重会增加待机主存，主动执行预热会增加启动时间和资源峰值，进一步卸载 Session 会增加下一句等待；这些都不能只以“优化”为名静默启用。显存档位、精度、分句、KV 容量和请求状态释放策略继续遵循原有选项，新的取舍先以显式配置验证。

完整推理进程退出、休眠启动、空闲休眠、唤醒合并和保活计时只由控制模式管理。它们不通过改写现有 `policy` 或默认启动脚本进入普通路径。可选模式的完成不阻碍已经独立验证的通用优化进入原实现。

## 原有直接模式的边界

| 当前能力 | 对后台使用的影响 |
| --- | --- |
| HTTP 启动创建 `Inference`，激活模型时调用后端 `load()` | 服务存活与 GPU 驻留绑定，尚无带模型配置的休眠启动 |
| `Model.load()` 只读取和检查模型描述，不加载 GPU 权重 | 可作为控制进程持有模型配置的基础，不代表完整运行校验已完成 |
| GPT / CuPy 在 HTTP 所在进程中执行，ORT 与经典日文前端已有独立 worker | 只退出声学 worker 无法清除 GPT 所在进程的 CUDA 上下文 |
| `NVIDIAEngine.unload()` 释放模型，`CUDAGPT.close()` 清空权重和空闲池 | 不等于整个推理进程退出；前端资源也可能继续占主存 |
| 默认 `direct` HTTP 拒绝总体 `policy="staged"` | HTTP 极限档需要显式启用 `managed`；低级 Engine 和 `tts` CLI 继续可用 |
| HTTP 单线程持有模型，冲突操作返回 409，流式输出有背压和断开取消 | 新生命周期需要保留这些所有权与输出约束 |

实现位置：[HTTP 生命周期](../src/sakuratts/server.py)、[Inference](../src/sakuratts/engine.py)、[CUDA 编排](../src/sakuratts/backends/cuda/engine.py)、[GPT 资源释放](../src/sakuratts/backends/cuda/gpt.py)。

现有 RTX 5060 记录中，FP16 标准、低显存、极限档的请求峰值分别约 758.2、584.1、465.1 MB，请求后空闲约 569.4、387.0、106.5 MB。空闲是请求后约 1 秒的观察；这些是准备好参考条件的 Engine 测量，没有覆盖 HTTP、首次陌生参考准备或长期驻留。详见 [推理档位](inference-profiles.md)。

其中极限档约 3.055 秒的热短句耗时是完整请求时间，不能当作纯唤醒耗时或 HTTP 首包延迟。已有低显存档约 1.009 秒、标准档约 0.234 秒的数据也不能直接用作新架构的首包承诺。

## 两种策略分别配置

运行模式先决定是否启用外层生命周期控制。默认模式沿用现状；控制模式再回答“什么时候持有资源”：休眠启动、提前唤醒、空闲多久后退出。

执行档位回答“生成语音时怎么使用显存”：保留模型、释放 GPT 请求状态、声学 Session 错峰、GPT 与声学模型错峰。保留现有档位与参数含义，不把新的空闲超时塞进现有 `policy`。

因此，在控制模式中，“说话时用标准档，空闲时深度休眠”是合理组合。它能降低一天中的总驻留时间，同时保留连续短句的速度。显存更紧张的机器可以显式选择低显存或极限档。选择执行档位本身不会启用控制模式，也不扩大默认模式已有的档位支持范围。

H 极限档的 HTTP 启动方式如下，`MODEL` 需替换为匹配 FP16 chunk256 声学包的模型目录或配置文件：

```powershell
sakuratts serve MODEL --experimental examples/minimum-vram.json --runtime-mode managed
```

H 在醒着空闲时也不保留 GPT 与声学权重，但曾经使用过 CUDA 的工作进程仍可能保留上下文。只有后续休眠退出整棵推理进程树，才能回收这些进程级资源；醒着空闲与休眠需要分别测量。

提前唤醒只能提前完成可复用的准备。极限档会在同一条请求内部交替卸载 GPT 与声学模型；若这些阶段必须互斥，无法通过请求前同时加载所有模型来消除重载，又维持原来的峰值。不能把“待机 GPU 接近零、活动峰值低于 500 MB、短句 200–300 ms”拼成当前已经验证的同一配置。

## 进程与状态

仅在控制模式中，让控制进程持有配置、当前模型选择、任务状态和空闲截止时间。控制进程不加载 NumPy、GPU 计算库或文本前端，PCM 传输也不需要这些依赖。将完整 `Inference` 放入可退出的推理进程，继续在该进程的单一执行线程中创建、调用和关闭引擎。文本前端、GPT、声学及参考准备的子进程都属于这棵受管理的进程树。

```text
任意调用方
    │ HTTP
控制进程：配置、状态、唤醒合并、空闲计时；不初始化 CUDA
    │ 有界 IPC
推理进程：Inference、文本前端、GPT
    ├── 声学 worker（现有运行库 ABI 边界）
    ├── 经典日文前端 worker
    └── 按需参考准备子进程
```

先复用现有计算路径和 worker 边界，不增加独立的 GPT 服务、角色服务或通用后端插件层。公开的进程内 `Engine` 继续适合短脚本与自行管理生命周期的调用方；它的 `close()` 不能因此宣称具有独立进程休眠效果。后续 Python 如需同样能力，可调用同一个进程控制组件。

控制模式通过 `/runtime` 公开资源状态 `sleeping → waking → awake → stopping → sleeping`，失败用 `failed` 表达；正在合成或切换模型另用操作字段表示。休眠期间模型仍然是“已配置”，但不能声称“已加载”。轮询任何健康或状态接口都不续期保活、不唤醒模型。

`awake` 表示所选档位准备完成。A / C / E 的 `preparation="model_load"`，完成原有模型加载步骤后 `model_loaded=true`；E 的声学 Session 仍按原策略在执行时创建。H 的 `preparation="runtime_init"`，仅完成推理进程、前端和配置准备，GPU 权重留到执行时错峰加载，所以 `model_loaded` 始终为 `false`，`model` 可以返回已选配置。`/health` 保留原有字段，使用相同的 `model_loaded` 含义；调用方结合 `/runtime` 判断准备情况，不能把这个布尔值当成逐时刻显存计量。

正常休眠仍是健康、可接收请求的状态。控制进程保存本次服务会话中成功提交的模型路径、参考准备设置与运行选项，睡醒不退回启动时的旧权重；这不改变原有“服务重启恢复启动配置”的约定，也不把预备参考变成 `/tts` 的默认参考。内存中的参考数组可以丢弃，匹配身份的磁盘缓存继续复用。切换失败仍需报告实际可用状态，不承诺旧权重被释放后自动回滚。

第一版先实现 awake / sleeping 两种稳定状态。保留 CPU 权重的中间状态会增加常驻内存与失效规则，等实际唤醒测量证明有必要后再加。原讨论中的约 159 MB CPU FP16 快照只是 GPT 数组成本，不能当成整个待机进程的 RAM 预算。

退出必须覆盖整棵自有进程树。Windows 应验证父进程异常退出时的子进程回收，例如用 Job Object 绑定生命周期；关闭管道不足以证明全部子孙进程已退出。先正常取消和清理，超过关闭期限后回收自有进程树。未确认退出前不能报告 `sleeping` 或启动一棵重叠的新推理进程树。

## 通用调用方式

以下路径及自动唤醒行为仅用于控制模式，默认模式访问 `/runtime` 路由返回 404：

| 接口 | 语义 |
| --- | --- |
| `POST /runtime/wake` | 提前准备当前配置的模型，可附有限的 `keep_alive_seconds`；不要求提供目标文本 |
| `GET /runtime` | 查询资源状态、模型是否配置、准备范围、错误与最近一次唤醒耗时 |
| `POST /runtime/sleep` | 空闲时释放推理进程树；已有合成、准备或切换操作时返回 409 |
| 原有 `GET/POST /tts` | 休眠时自动唤醒；正在唤醒时等待同一次准备，然后合成 |

`wake` 可以不带请求体，或传 `{"keep_alive_seconds": 60}`，允许 0 至 3600 秒，默认 60 秒。状态响应包含 `state`、`preparation`、`model_configured`、`model_loaded`、`model`、`worker_pid`、`busy`、`last_error`、`last_wake_ms` 和 `idle_sleep_seconds`。最近一次成功唤醒耗时与准备范围分别记录，不能把 202 响应时间当作唤醒耗时。

`wake` 默认快速返回：开始或正在准备时返回 202，已经就绪时返回 200。202 只说明任务被接受，不表示模型可立即计算。调用方可以查询状态，也可以直接提交 `/tts`；不必先轮询到就绪。第一次准备失败需要有明确错误，等待它的合成也必须结束，不能无限挂起。

未配置模型时直接返回配置错误，不创建 worker。唤醒和进程握手设总超时，不响应也必须进入失败处理并回收已创建的进程；禁止后台无限自动重启，下一次显式唤醒或合成可在清理完成后重试。

同一模型、配置版本的重复唤醒合并为一次操作。合成到达正在进行的唤醒时，占用唯一的合成位置并等待；第二个合成仍按现有约束返回 409，不建立无界队列。模型切换与唤醒串行，避免把旧模型的完成通知当成新模型已经就绪。

尚在等待唤醒的合成若被取消或检测到客户端断开，应释放其合成位置，唤醒完成后不再执行它；共享唤醒可继续并按保活规则回收。已经进入推理的请求仍需等计算取消和清理完成后才释放位置，不能让新请求与旧计算重叠。

控制模式下，正常请求无需依赖 `wake` 才能成功。预热是可选的延迟优化，不能成为新的调用前置步骤。原版 `/tts` 的字段、音频格式和不支持参数的报错保持原有约束；新增模式的生命周期需要补充独立契约，不改写默认模式的约定。

以请求云端大模型的客户端为例：

```text
开始请求大模型 ────────────────── 获得可朗读文本
     └─ 同时调用 wake ── 准备 TTS ──────┘
                                      └─ /tts ── 首段 PCM
```

调用方并行发起两项工作，不等待 `wake` 完成才请求大模型。流式大模型可在得到适合朗读的一句时提交 TTS；断句、播放与跨请求音频队列由调用方管理，TTS 不解析大模型协议。

若提前量为 `T_lead`，本次所需且可复用的唤醒准备耗时为 `T_wake`，就绪后到首段 PCM 的时间为 `T_speech`，在不存在其他争用时：

```text
文本就绪后的等待 ≈ max(0, T_wake - T_lead) + T_speech
```

还未提供的参考条件、与本次形状相关的图捕获等必须计入剩余准备或 `T_speech`，不能从计时中消失。若上游是本地 GPU 大模型，提前唤醒可能造成资源争用，应由调用方决定提前时机；TTS 不默认检测或抢占其他程序的显存。

## 预热与保活的具体约束

准备就绪与执行预热分开记录。A / C / E 可以提前完成进程启动、资源校验、权重上传和档位允许保留的 Session 创建；H 只完成进程、前端和配置准备，权重上传与 Session 创建留在每片段执行路径。没有参考音频和参考文本时，不能宣称声音条件也已就绪。

真正的执行预热需要走过适当的 Prefill、Decode 和声学路径。当前 CUDA Graph 在首次 Decode 捕获，`release-state` 又会清除 Graph、KV 和工作区；`staged` 还会销毁模型或 Session。跑一次示例后立刻释放这些资源，并不能保证下一句全部热启动。只保留经测量确实有收益、符合所选显存档位的准备结果。

当前先按档位公开实际准备范围，单独测量首句剩余开销，再决定是否加入执行预热。执行预热若采用固定输入，需隔离 RNG、清理请求状态、不输出音频，并验证固定种子的真实请求不会受其影响。预热的峰值也算服务峰值。

已知参考可复用现有参考缓存；完整参考预备能力可以在后续通过相同参考字段扩展，避免引入桌宠专用角色注册协议。陌生参考可能启动含 PyTorch 的编码进程，应单独报告其时间和峰值；模型准备完成不能掩盖这项成本。

空闲与保活计时使用单调时钟，遵循以下规则：

- 保活截止时间从唤醒完成起计算，或在已唤醒时从提示到达起延长；重复提示不能缩短原有窗口。显式提示可以续期，但每次窗口由服务设置上限。
- 合成、模型切换、参考准备、等待唤醒的已接收请求都会阻止自动休眠。空闲超时从最后一次操作完成起计算，不从请求到达起计算。
- 只有无活动操作、无等待者、空闲期限和保活期限都已过时，才自动休眠。60 秒空闲超时是可配置起点，需要结合调用频率测量。
- 大模型失败、用户取消或最终不需要语音时，保活自动过期，不强制客户端发送“释放”请求。共享客户端不应为了取消自己的预测而让整个服务睡眠。
- `sleep` 是显式服务级操作：无活动操作时可以提前结束保活，重复休眠成功返回；忙碌时不截断音频。管理客户端使用它，普通请求依靠超时回收。
- 空闲定时器、唤醒和请求接收在同一个控制入口串行修改状态；旧定时器必须复核当前版本与截止时间。新请求遇到已经开始的退出时，等待退出后再唤醒，不能边退出边访问旧引擎。

每次启动分配新的 worker 代次，控制进程忽略旧代次迟到的 ready、音频和完成通知，避免旧进程覆盖新状态。待机只需要事件驱动的截止时间，不做高频 GPU 查询、周期性试跑或循环重新校验模型。IPC 保留有界音频背压、请求编号和终态；客户端断开后取消所属计算，已开始的流不能因 worker 重启而悄悄重播。

## 当前实现与后续顺序

当前保留默认模式，新增 `managed` 控制服务与完整推理 worker，提供自动唤醒、提前唤醒、保活、空闲休眠和状态查询。控制模式已接入 H 极限档，准备范围与模型加载状态分开报告。旧命令、配置与启动器无需迁移；两种模式仍共用原有计算链路。单元测试验证生命周期和默认兼容，不能替代 GPU、音频及长期运行验收。

接下来按以下顺序验证和扩展：

1. 用当前 HTTP 可用档位测量流式首段延迟、完整进程树回收和反复睡醒，覆盖失败、取消与模型切换。
2. 对照控制模式各档位的活动显存、醒着空闲占用和每片段延迟，比较运行环境准备、模型加载与执行预热收益，再决定是否提供可选 CPU 权重缓存；对加载路径的通用优化分别验证后共用。
3. 按测量结果继续优化 KV 容量和 Prefill 临时缓冲。KV 分桶必须容纳文本、参考前缀和允许的生成长度，不能仅按“短句”猜测 512 容量并截断；无法安全预估时沿用现有容量。这类算法与容量策略不随模式切换自动启用。

控制模式的后台测量先显式选择现有标准档加深度休眠作为延迟对照，低显存与极限档继续作为活动峰值的取舍。这不改变任何模式未指定精度时的 FP32 默认。FP16 仍沿用当前实验与音质验收状态，不因新增生命周期就改称已完成质量验收。部署、第二台机器验证和参考准备仍按现有路线推进。

## 验收与测量

复用 [基准协议](specs/benchmark-protocol.md)，扩展 [Windows 显存采样工具](../research/tools/windows_low_vram.py) 的进程树观测。外置采样器需要跟踪控制进程和每次更换的 worker PID；产品本身不为了计量持续唤醒 GPU。

先验证默认模式：省略新选项与显式选择默认模式行为一致；配置模型时仍在启动加载；没有新增外层推理进程、空闲退出定时器或运行控制路由；长时间空闲后不承担新增的进程重启成本。现有 HTTP、CLI、Python 和整合包入口的默认配置均纳入检查，已有健康字段、默认精度、409、音频输出及失败行为不因模式引入而改变。两种模式共用代码的修改须同时运行原有回归。

以下新增生命周期场景均显式启用控制模式；测量结果同时标明运行模式与执行档位：

| 场景 | 必须观察的结果 |
| --- | --- |
| 带有效模型配置启动后保持休眠 | 控制服务可访问；不创建推理 worker，不初始化 CUDA，不加载前端大型资源 |
| 无提前提示的 `/tts` | 自动恢复并返回正确音频，完整记录冷请求首段 PCM 延迟 |
| 提前 0、0.5、1、2、5 秒唤醒后合成 | 记录唤醒开始/完成、文本提交、首段有效 PCM，比较剩余等待与同档位基线 |
| 唤醒后没有合成，或连续短句后停止 | 保活/空闲期限到达后退出整棵推理进程树；睡眠后 30 秒、5 分钟仍无残留 |
| 连续唤醒和反复睡醒 | 建议至少 100 轮，记录失败率、句间延迟、进程数量、句柄和内存趋势；再做数小时待机与间歇请求 |
| 唤醒与合成/睡眠/切换同时到达 | 不重复启动，不误用旧模型，不在活动请求中释放资源；第二个合成仍遵守并发限制 |
| 取消、流式背压、加载失败、worker 或宿主异常退出 | 有明确终态，资源可回收，后续请求可按约定重试，已发送音频不自动重播 |
| 固定输入、参考、种子与执行档位 | 比较直接合成、提前唤醒、睡醒后合成的 token、PCM 和停止结果，验证生命周期不改变音频行为 |

资源同时记录 Dedicated / Shared GPU Usage、进程树 RSS 与私有提交、空闲 CPU 时间增量及唤醒次数。GPU 计数缺失或无可用采样时标为不可用；只有确认进程退出和测量有效，才能说明 TTS 的 GPU 分配已回收，不能将空数组填成零。

无 GPU 的单元测试可覆盖唤醒合并、超时和故障回收、休眠竞态及配置恢复。复用 [HTTP 测试](../tests/test_server.py) 的单请求与断连所有权检查、[声学进程测试](../tests/test_ort_process_lifecycle.py) 的异常消息与关闭检查，以及 [推理失败测试](../tests/test_nvidia_failure_lifecycle.py) 的取消后恢复检查。实际 GPU 释放、提前量收益和音频一致性仍需在目标机器验证。

首包以客户端收到第一个非空、可消费的 PCM 为准；HTTP 头、WAV 空头、202 响应都不算音频首包。记录 p50 / p95、样本数及失败，区分无编译缓存首次启动、有磁盘缓存的进程冷启动、提前唤醒和连续热请求。

再比较典型使用周期中的显存占用积分（MB·s）、平均主存、后台 CPU 与无效唤醒次数，同时保留峰值。这样可以判断“多保活一分钟”是否值得，而不会为了压低单次峰值让每句话都变慢。共享 GPU 的共存影响单独测量，不能以整个系统空载推断桌宠实际体验。

首轮 HTTP 进程隔离测量已记录控制服务的 RSS、私有提交和模型加载耗时，见[实测记录](../research/notes/managed-runtime-20260922.md)。具体主存预算还需结合目标机器和长期运行确定。当前空闲与保活默认各 60 秒，后续调整需要说明测量依据。现有数据不足以承诺零 RAM、唤醒必然被上游延迟完全覆盖或任意文本低于 500 MB。
