# 三处 GPT 概率超差的 logits 来源

日期：2026-09-19。十例自有生成已发现三处采样概率超差，参见 [扩展生成对照](2026-09-19-expanded-native-generation.md)。此前把全部 1805 步官方 logits 送入同一 NumPy 采样器，概率均通过原容差。本轮不再更换采样器，而是检查失败步骤中哪些 logits 的差异推动了概率变化。

## 只使用已保存的输入

`harness/gpt_probability_sensitivity.py` 读取 `130029.229727Z-native-gpt-generation` 的 logits 和历史，以及 `125743.942661Z-official-mps` 的官方 trace、概率。先核验原 `probability-attribution.json` 所指清单、相关 trace 和数组哈希，确认完整 token 历史相同，并确认采样源码与原运行快照相同。

脚本展开重复惩罚、温度和 Top-k 分数，再逐位核对其概率结果与现有采样器，三处失败均精确复现。没有加载模型、PyTorch 或 MLX，也没有修改原始运行目录。原概率阈值仍为 `atol=1e-6, rtol=1e-5`，logits 阈值仍为 `atol=1e-4, rtol=1e-5`。

三步都保留相同的 15 个 Top-k token，全部保留 token 均未出现在此前历史中，重复惩罚没有作用于这些分数。当前失败不是过滤集合或惩罚分支发生改变。

## 目标 token 与其他 token 的共同影响

softmax 概率取决于整个保留集合。只看失败 token 自身的 logit 误差，会漏掉分母变化。脚本用 FP64 计算一阶敏感度 `δp_i ≈ p_i(δz_i − Σp_jδz_j)`，并用单独替换目标 logit、单独替换其他 logits 的 FP32 计算作交叉检查。这些只是误差归因，不是新的推理或验收算法。

| 样例 / 从 0 开始的步骤 / 目标 token | 实际概率变化 | 一阶预测 | 目标自身贡献 | 其他 token 合计贡献 |
|---|---:|---:|---:|---:|
| ja-long / 274 / 857 | -3.59118e-6 | -3.57015e-6 | -9.48035e-7 | -2.62212e-6 |
| zh-punctuation / 95 / 327 | -1.780689e-6 | -1.780285e-6 | -8.57796e-8 | -1.69451e-6 |
| zh-punctuation / 97 / 801 | -2.01911e-6 | -2.01143e-6 | -2.35552e-6 | +3.44089e-7 |

一阶预测与实际 logits 传播量的残差分别约为 `8.77e-9`、`-4.04e-10`、`7.23e-9`。表中的“实际概率变化”还包含官方与 NumPy 在相同 logits 下的微小差异，分别为 `-2.98e-8`、`0`、`-1.49e-8`。这些量级不能解释主要偏差。

日文第 274 步，目标 857 的 logit 仅下降 `7.62939e-6`，但保留集合的概率加权平均变化为 `+1.69241e-5`。最高概率 token 470 的 logit 增加 `2.47955e-5`，其官方概率约 0.571，单独贡献约 `-2.05848e-6`，占其他 token 贡献的大部分。因此目标概率下降主要来自竞争分数上升。只替换目标 logit，概率约下降 `9.38773e-7`；只替换其他 logits，约下降 `2.60770e-6`。

中文第 95 步也主要受其他分数影响。目标 327 的 logit 下降 `1.19209e-6`，而加权平均变化为 `+2.16178e-5`。token 44 的 logit 增加 `3.40939e-5`、官方概率约 0.242，对目标概率贡献约 `-6.43538e-7`。其他 token 的总影响明显大于目标自身。这一步实际仅比允许误差多约 `2.01e-10`，仍如实保留失败。

中文第 97 步的情况不同：目标 801 的 logit 下降 `3.09944e-5`，成为主要来源；其他 token 的变化反而补偿约 `3.44e-7`。所以不能用单一 token 或统一的概率偏置修复这三步。

全部 Top-k 分数、原始 logits、概率、误差、历史成员关系和相邻两步的结果均保存在新目录：`runs/20260919T134342.190358Z-gpt-probability-sensitivity/`。三处目标相对保留集合加权平均的分数变化均约为 `-2.3e-5` 至 `-2.5e-5`；这个接近的结果描述的是概率敏感度，尚不能说明它们来自相同的 GPT 算子。

## 保留的后续诊断入口

按 Windows/CUDA 优先的研发方向，暂缓进一步 Mac 舍入追踪，保留这三处失败和以下诊断入口。需要重新调查时，先捕获输出投影前的完整隐藏向量和投影后完整 logits：官方使用真实 `ar_predict_layer` 的输入/输出 hook，自有运行时使用 `_linear(..., "output")` 的输入/输出。首轮保留失败步骤及相邻步骤，避免只记录失败 token；前两处主要由竞争 token 驱动。

| 样例 | 失败步骤 | 当前步输入 token | 文本长度 / 参考语义长度 | 当前有效 KV 长度 |
|---|---:|---:|---:|---:|
| ja-long | 274 | 320 | 314 / 113 | 701 |
| zh-punctuation | 95 | 696 | 104 / 113 | 312 |
| zh-punctuation | 97 | 219 | 104 / 113 | 314 |

捕获必须先逐位复现原 trace 与 native run 的目标 logits，随后将相同隐藏向量送入两端输出投影，判断本地线性运算贡献与上游隐藏状态贡献。只有后者确有贡献时，再逐层保存对应 decode 步骤的输出，并把注意力所用 KV 分为文本、参考前缀和已生成 token 三段，定位哪段误差被关注。

现有 `diagnose_mlx_step.py` 默认加载 FP32 prefill，而本次 native run 使用 CPU FP64 prefill；不能原样套用，否则诊断起点已变。官方转录图也只有在复现真实官方模块输出后才能作为中间结果依据。本轮没有执行这些模型捕获，尚未把问题归到某一层、KV 位置或线性算子。
