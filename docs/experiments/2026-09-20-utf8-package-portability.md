# 包元数据统一使用 UTF-8

日期：2026-09-20（Asia/Shanghai）。可搬迁验收包完成后，继续核对日文运行入口的文件读取。发现 CLI、参考条件、GPT / SoVITS 包以及开发转换工具的部分 JSON 读写依赖系统默认编码。

## 复现与修复

在 Mac 进程中把未指定编码的 `io.open` 切换为 CP932 或 CP936，读取现有四个真实包。CP932 下前端包正常，参考包报 `UnicodeDecodeError`，GPT 和 SoVITS manifest 虽能解析，来源文字却与 UTF-8 原文不同。CP936 下参考、GPT 和 SoVITS 包均报解码错误。原异常与 traceback 保存在 `before.json`、`before-reproduced.json`。

修复在日文运行链及相关转换 / 参考准备工具中明确指定 UTF-8，合计 10 个文件、20 处读写。没有替换 Unicode 字符，没有转存现有包，也没有修改权重、音素或计算精度。中文专项代码未扩展。

修复后同样八次读取全部与直接 UTF-8 读取一致。两个参考准备工具的真实 JSON 写入函数也分别在两种编码模拟下测试：旧函数四次均报编码错误；新函数四次输出均与预期 UTF-8 字节相同。这里只验证写入函数，未重跑完整模型转换或参考编码。

## 真实运行

使用修复后源码快照，在 CP932、CP936 默认文本编码模拟下分别运行日文 CLI，原输入为：

> こんにちは。今日はいい天気ですね。よろしくお願いします。

两次均使用现有四个包、NumPy seed 0 和默认分阶段加载，进程退出 0。模拟同时覆盖 Python 的 `io.open` 和 `builtins.open`；实际机器仍是 Mac，不能据此宣称 Windows 安装或 CUDA 推理已经通过。

两份 WAV 与旧分阶段 seed 0 基线逐字节相同；原文、phones、参数、生成计数与停止摘要一致。旧基线用较早的前端导出包，manifest 的语言模型来源路径不同，但三个实际运行资源的哈希与字节数一致。这里按同资源对照，不声称两份前端 manifest 相同。本轮编码修复前后使用的四个包保持原哈希。

另以默认 FP32 声学路径重跑四例可搬迁验收，候选生成退出 0，比较退出 1，保留既有长句概率与标点 MRTE 超差。局部声学包测试四项通过。

与上一轮 FP32 候选逐数组比较，803 个输出的 dtype、shape 和原始字节全部相同。10 个修改文件去掉新增 UTF-8 参数后的 AST 与改动前相同，没有混入计算改动。
