# G2PW 输入准备迁移

日期：2026-09-19。`src/sakuratts/g2pw_inputs.py` 已接手字符映射、查询截断和六组 ONNX 输入数组的准备。本轮使用自有 `ChineseBertTokenizer`，没有导入 PyTorch、Transformers 或 ONNX Runtime，也没有加载 G2PW 模型。

## 代码来源与接口

迁入代码来自官方 GPT-SoVITS 提交 `48b1a0169a28582a8984402f82cf438d3bfa6aca`：

- `GPT_SoVITS/text/g2pw/utils.py`：`wordize_and_map`、`tokenize_and_map`。
- `GPT_SoVITS/text/g2pw/dataset.py`：输入打包、两种截断和两种标签映射，共 5 个函数。
- `GPT_SoVITS/text/g2pw/onnx_api.py`：提前构建字符 ID 与 phoneme mask 的实例生命周期。

7 个迁入函数的 AST 与原函数一致。文件保留 PaddlePaddle 的版权、Apache-2.0 声明及 GitYCC/g2pW 来源；完整 Apache-2.0 文本位于 `docs/third-party/Apache-2.0.txt`，官方项目 MIT 文本继续保留在 `docs/third-party/GPT-SoVITS-LICENSE.txt`。这份代码来源记录不替代模型和词典的分发许可核对。

`G2PWInputs(tokenizer, polyphonic_chars, use_mask=True)` 只在创建时构建标签、`char2id` 和 phoneme mask。调用 `prepare(texts, query_ids)` 返回官方同名的六组数组；调用方需要给出已经准备好的文本和非空查询列表。没有查询时，完整前端应沿用官方行为，直接返回无需模型处理的部分结果。

复用范围与官方相同：一次请求内，同一小写文本共用分词和字符映射；短句还共用输入 ID。超过 510 个内容词元后，各查询分别截取并转换 ID。文本缓存随这次请求结束，字符 ID 和 mask 随 `G2PWInputs` 实例保留。没有新增跨请求文本缓存。

本轮采用实际模型的 `use_char_phoneme=False`。另一个标签辅助函数随原代码保留，尚未建立 `use_char_phoneme=True` 模型路径的对照。

## 实际验证

Harness 的官方 `prepare` 仍从固定源码提取原函数作为对照；候选 `validate` 已直接调用 `sakuratts.g2pw_inputs.G2PWInputs`。候选执行不再借用官方 Python 函数，仅读取已保存的多音字表和预期输出。

先使用上一轮 tokenizer 对照验证基础结果，再新建对照覆盖窗口、mask 开关和变长批次：

| 检查 | 结果 |
|---|---|
| 原有 18 条文本的词元、ID、双向字符映射 | 18 / 18 完全一致 |
| BERT 三组输入 | 54 / 54 完全一致 |
| 17 条带查询文本的 G2PW 六组输入 | 102 / 102 完全一致 |
| 相同 17 条文本，启用 32 字查询窗口 | 102 / 102 完全一致 |
| 相同 17 条文本，关闭 phoneme mask | 102 / 102 完全一致 |
| 短句、600 字长句、重复短句组成的变长批次 | 6 / 6 完全一致 |

共 366 组数组的形状、数据类型和元素全部一致。600 字输入覆盖开头、中间和末尾查询；原用户报告的中日文输入保持不变。

另用计数 tokenizer 检查同句多查询：

| 输入 | 一个查询：分词 / ID 转换调用数 | 三个查询：分词 / ID 转换调用数 |
|---|---:|---:|
| `你好，今天重新开始。` | 10 / 1 | 10 / 1 |
| 600 个“重”字 | 600 / 1 | 600 / 3 |

候选和官方计数相同。下一次请求会重新分词，未把临时缓存变成常驻资源。这里的分词次数按 `tokenize(word)` 计数，不能解读为模型推理次数。

最终证据位于参考目录的 `runs/`：

- `20260919T123404.565363Z-tokenizer-equivalence/`：固定官方代码、表和 tokenizer 快照，预期映射及数组、版本、命令和原始计时。
- `20260919T123432.273993Z-tokenizer-candidate/`：自有代码快照、366 组比较结果、缓存调用计数及来源审计。
- `20260919T123125.321570Z-tokenizer-candidate/`：自有实现复查上一轮 18 / 156 对照的记录。

## 资源和计时口径

官方与候选这次都提前建立字符 ID 和 mask，再进行 2 次热身、5 次整批计时。每轮仍包含 18 条文本的 tokenizer、字符映射、输入打包和 BERT 输入编码，未计入神经模型。

| 诊断项目 | 官方接口 | 自有接口 |
|---|---:|---:|
| 输入准备器初始化 | 157.50 ms | 155.07 ms |
| 18 条文本整批中位耗时 | 28.51 ms | 12.95 ms |
| Harness 进程生命周期最大 RSS | 201.58 MiB | 147.63 MiB |

官方初始化还包含 AST 提取，候选初始化包含本地模块导入。两环境的 NumPy 版本不同，且其他研发任务可能并行；这批诊断数字不能直接作为完整前端或 TTS 的速度、常驻内存收益。

上一轮 tokenizer Harness 在每次打包时重建默认 mask，整批计时约 2 秒；本轮恢复了官方实例已有的静态表复用。因此不能将这个跨轮时间差写成 SakuraTTS 新增的优化。RSS 包括扩展分支、对照数组和框架导入差异，不是模型占用或 GPU 峰值。
