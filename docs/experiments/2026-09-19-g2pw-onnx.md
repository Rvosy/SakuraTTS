# G2PW 独立 CPU ONNX 对照

日期：2026-09-19。自有 `G2PWSession` 已在当前 Mac 上执行原始 `g2pW.onnx`。8 组固定输入分别走默认去重和不去重路径，共 16 组概率数组与官方逐位一致，标签和置信度也完全一致。官方与候选各自在独立进程中运行，外层记录的退出码均为 0。

## 实现范围

`src/sakuratts/g2pw_session.py` 接收明确的本地模型路径和有序标签，构造时才导入 ORT、加载模型。`run(inputs)` 返回原始概率；`predict(inputs, texts)` 默认沿用官方按句去重，再返回标签和置信度；`close()` 释放该实例持有的 Session。

设置与固定官方提交 `48b1a0169a28582a8984402f82cf438d3bfa6aca` 一致：

- `CPUExecutionProvider`、`ORT_ENABLE_ALL`、`ORT_SEQUENTIAL`、intra-op 线程数 2；inter-op 保持官方默认值 0。
- 使用 ORT 1.30.0，实际 build commit 为 `f2c39fe`。导入前设置进程局部 `ORT_DISABLE_TELEMETRY=1`，沿用已验证的 macOS 退出处理。
- 六组输入名称映射、`argmax` 标签顺序、置信度和默认去重保留原语义。去重方法的 AST 与官方一致。

原始模型没有转换或覆盖，文件大小 635,212,732 字节，SHA-256：

```text
2eb3c71fd95117b2e1abef8d2d0cd78aae894bbe7f0fac105ddc9c32ce63cbd0
```

这个接口不负责完整 G2PW 文本预处理。当前实验从已保存的固定数组开始，不能据此宣称原始中文到最终音素或语音的完整前端已经独立运行。

## 正确性与长文本边界

五组输入来自既有官方规范化中文：固定失败样例、长句、标点句和两个混合文本中的中文段。另有一个含重复句的变长批次，以及 511 / 600 词元的异质边界。

| 对照 | 结果 |
|---|---|
| 官方与自有实现：默认去重概率 | 8 / 8 逐位一致 |
| 官方与自有实现：不去重概率 | 8 / 8 逐位一致 |
| 两种路径的标签和置信度 | 16 / 16 完全一致 |
| 模型 SHA、ORT build 和执行设置 | 相同 |
| 两个进程的实际退出码 | 均为 0 |
| 两个推理进程导入 Torch / Transformers | 均为 false |

概率输出类型为 FP32。预设比较容差为 `rtol=1e-5, atol=1e-6`，实际最大误差为 0，没有放宽容差。

此前纯输入发现的长文本去重边界会影响模型输出。两种运行环境观察到相同结果：

| 人工边界 | 默认去重与不去重的概率最大绝对差 | 标签差异 |
|---|---:|---|
| 511 内容词元 | 0.275589 | 末查询：默认 `ㄔㄨㄥ2`，不去重 `ㄓㄨㄥ4` |
| 600 内容词元 | 0.322720 | 中间、末查询均出现同样变化 |

其他六组中，去重和不去重的概率逐位相同。这确认了边界对预测的影响，但不代表人工长串中哪一种读法是正确答案。默认官方行为继续保留；没有把这项发现解释成原短句漏句或“你好”问题的原因。

## 安装与资源记录

在参考目录现有 `.venv-mlx-macos` 中只新增了 `onnxruntime==1.30.0`、`flatbuffers==25.12.19`、`protobuf==7.36.2`。没有更新已有包，也没有安装 Torch、Transformers 或下载模型，`pip check` 通过。

安装文件增量为 85,541,896 字节，约 81.58 MiB，包含本次环境生成的文件；它与只读审计中的旧环境文件大小不同。安装命令、wheel 来源与哈希、前后清单和检查日志保存在 `runs/20260919T124746.129650Z-g2pw-ort-install/`。候选运行包仍未制作，不能把这个增量当成最终安装体积。

| CPU 进程边界 RSS | 官方进程 | 自有进程 |
|---|---:|---:|
| ORT 导入后、Session 创建前 | 54.23 MiB | 49.08 MiB |
| Session 加载后 | 1325.25 MiB | 1316.72 MiB |
| 完成全部诊断后 | 1361.88 MiB | 1354.61 MiB |
| 释放 Session 并 GC 后 | 519.94 MiB | 512.67 MiB |

这些是进程 RSS 边界。OS 生命周期最大 RSS 包含导入、加载和诊断，也另存于结果；不能把边界称为阶段峰值，更不能当成 NVIDIA 独立显存。

原模型即使脱离 Torch，仍带来约 1.3 GiB 的加载后进程 RSS。Session 释放后也没有回到初始值；本轮尚未定位剩余占用来自 ORT 进程资源、分配器保留或其他对象，下一轮需要单独验证生命周期。

Session 构造分别为 230.06 ms 和 204.32 ms，不含模型哈希检查；OS 文件缓存可能已热，不能称为整应用冷启动。候选五段普通中文的单次默认去重诊断约 7.17–25.28 ms。计时包含保存概率副本的插桩，且本轮没有多次热运行中位数，因此只保存原始时长，不把差值归因为速度提升。

## 证据与复现

主证据目录：`SakuraTTS-References/runs/20260919T125451.773385Z-g2pw-session/`。

- `prepared.json`、输入 NPZ、源码快照：固定输入、来源和哈希。
- `official/`、`native/`：每次 Session 调用的原始概率、按查询恢复顺序后的概率、标签、置信度、设置及资源边界。
- `execution.json`、两个 `.log`：子进程命令、实际退出码和原始日志。
- `comparison.json`、`dedup-effects.json`：两实现对照和已保存输出的去重差异。
- `source-audit.json`：测试代码快照一致，默认去重 AST 与官方一致。
- `postvalidation-source-audit.json`：测试后只补充模块说明中的上游 URL 和许可关系，执行 AST 未变。
