# 可选的推理进程生命周期控制

状态：已采用，2026-09-22。适用于 Windows / NVIDIA HTTP 服务的首版 `managed` 模式。

## 原因

后台应用长期没有语音请求时，继续持有 CUDA 上下文与前端资源没有必要。现有模型卸载和显存池回收无法保证消除进程级占用；同时，已有调用方需要保持启动加载和连续请求的原有行为。

## 决定

保留默认 `direct` 模式，新增启动时显式选择的 `managed` 模式。默认模式仍在 HTTP 的专用线程里使用 `Inference`；控制模式把完整 `Inference` 放到可退出的工作进程，HTTP 进程只管理请求、状态和生命周期。两种模式共用配置读取与推理代码，运行模式不改变精度或显存档位。

提前唤醒是可选提示，直接提交合成也能自动加载。同一轮唤醒合并，等待唤醒的合成占用唯一请求位置。空闲期和保活期都结束后退出自有推理进程树；状态查询不延长驻留。所有超时、取消和输出背压都保留工作所有权，计算和清理完成前不接收第二个合成。

IPC 使用有长度上限的 JSON 和 PCM 数据，发送与接收队列有界，不使用 pickle。Windows 在发送初始化消息前绑定 Job Object；控制进程异常退出时由系统回收该作业，工作进程异常退出时由被动等待线程回收子孙。退出失败时保留所有权，不把它报告为休眠。

唤醒的准备范围遵循执行档位。A / C / E 为 `preparation="model_load"`，完成原有模型加载步骤；H 的总体 `staged` 只在 `managed` 中开放，标记为 `preparation="runtime_init"`，唤醒只准备推理进程、前端和配置，权重仍在执行时交替加载。H 的 `model_loaded` 始终为 `false`，调用方结合 `state="awake"` 和准备范围判断就绪，不能误以为全部 GPU 权重已经驻留。默认 `direct` 仍拒绝总体 `staged`。

所有档位都不把准备完成当成执行预热：CUDA Graph、未知参考条件和首次执行仍可能产生额外开销。CPU 权重快照及更深的预热留待独立验证。控制进程不加载 NumPy、GPU 计算库和文本前端；解释器与 HTTP 服务仍占主存。

## 代价

控制模式需要额外的 HTTP 进程、IPC 拷贝及睡醒后的加载时间。完整模型、前端和编译缓存的首次执行开销不会因进程隔离消失。H 档降低活动显存，但每片段重载模型的等待不能被一次提前唤醒消除。保留 CPU 权重或延长保活能减少等待，但会增加后台主存或显存驻留，不默认启用。

Python 进程内 `Engine` 的生命周期保持原状。默认模式不承担新增完整推理进程与自动休眠成本；能独立证明有效的加载、复制和资源清理优化可以由两种模式共用。
