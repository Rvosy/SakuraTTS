# ADR 0004：分开模型描述、执行后端、语言与发行组合

状态：已接受。日期：2026-09-22。更新 [ADR 0002](0002-product-layout.md) 中的后端与前端边界。

## 原因

原公共 Engine 直接构造 NVIDIAEngine，Model 在读取元数据时只允许 CUDA 和日文。经典日文前端的解释器又借用了声学解释器字段。增加中文或其他设备时，这些限制会迫使调用入口、模型描述、前端和打包脚本同时修改。

Windows 完整包已经按需启动 CPU 准备环境，用于原始权重转换和新参考编码。后续设备和语言不应继续累加到这个包中。用户需要选择适合设备和语言的发行组合，同时保留现有命令、`direct` 模式和 FP32 默认行为。

## 决定

Model 只描述内容与建议配置，读取时检查必要字段、资源路径和参考名称关系，不加载设备库。执行时由 `backends.create_runtime` 选择 Runtime，后端自身解释实验选项。实现表写在源码中，当前只有 `cuda`，不增加插件扫描、动态注册或自动设备回退。未知后端在原始权重转换前拒绝，避免先进行无用的转换。

前端独立装配。语言 profile 提供已实现语言的模式与文本规则，处理器负责规范化、音素和特征，`FrontendRuntime` 负责资源和进程生命周期。当前只装配日文；中文研究代码继续保留，但不列入能力清单。共享请求准备和参考转写使用相同语言定义。

`frontend_python` 与 `acoustic_python` 分开表示工作进程角色。旧配置缺少 `frontend_python` 时继续复用声学解释器；发行 recipe 可让两种角色指向同一份 Python，以控制磁盘体积。Model 不再隐式绑定整合包路径，执行适配器根据当前安装清单绑定位置。

发行 recipe 记录目标平台、执行后端、语言、服务和工作进程位置。当前只有 Windows x64 / CUDA / 日文目标，HTTP 服务与准备组件可省略。构建从明确指定的本地组件装配，不联网补依赖。新增组合必须先有对应实现和运行组件，再进入构建支持表。

校验放在拥有信息的边界：Model 检查描述和资源目录，后端与前端检查各自实际使用的模型及资源，构建检查发行文件闭包。共享入口不重复枚举 CUDA 的实验参数，也不重复判断已经由 Model 识别的格式。资源身份、文件范围、张量形状、IPC 长度和进程所有权仍影响正确性，继续保留。

## 当前范围与后续成本

本决定只调整装配边界，CPU、AMD、Apple 和中文整链仍待实现。`capabilities` 返回已实现的适配器和语言，不能替代驱动、依赖或真实推理检查。默认 direct / FP32、原版 HTTP 字段、请求串行所有权、取消和 managed 睡醒语义不变。

新增设备需要交付 GPT 与声学运行实现、模型转换适配、资源准备和目标系统的工作进程，再验证全部公开入口。CPU ORT 声学只覆盖其中一段；MLX 研究模块也不能直接作为完整 macOS 发行版。新增中文还需要 BERT、G2PW 和语言资源转换，验证目标文本、参考转写与混合语言的音素对齐。本地上游核查见[源码核查记录](https://github.com/Rvosy/SakuraTTS/blob/main/research/notes/architecture-audit-20260922.md)，开发顺序见[路线图](../roadmap.md)。

GPT-SoVITS 的权重与参考条件契约、Windows 转换器继续复用。它们属于当前模型家族和已交付链路，不提前拆成通用插件系统。将来真正加入第二种实现时，再依据两者共同需要的接口调整。不同组合分别测量体积和性能，不承诺把全部语言与设备依赖一起装入 2 GB。
