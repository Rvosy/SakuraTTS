# ADR 0004：分开模型描述、执行后端、语言与发行组合

状态：已接受。日期：2026-09-22。后续 CPU / DirectML 扩展见 [ADR 0005](0005-cpu-directml-runtime.md)。更新 [ADR 0002](0002-product-layout.md) 中的后端与前端边界。

## 原因

原公共 Engine 直接构造 NVIDIAEngine，Model 在读取元数据时只允许 CUDA 和日文。经典日文前端的解释器又借用了声学解释器字段。增加中文或其他设备时，这些限制会迫使调用入口、模型描述、前端和打包脚本同时修改。

Windows 完整包按需启动 CPU 准备环境，转换原始权重或编码新参考。设备运行库可以跨语言共用，语言模型则按发行组合加入，使只用日英的用户可以继续使用较小的包。

## 决定

Model 描述内容与建议配置，读取时检查必要字段、资源路径和参考名称关系。执行时由 `backends.create_runtime` 按源码中的后端表选择 Runtime，具体设备实现解释自己的执行选项。未知后端在转换权重前报错。

前端独立装配。语言 profile 提供已实现语言的模式与文本规则，处理器负责规范化、音素和特征，`FrontendRuntime` 按模型资源清单装配处理器并管理其生命周期。日英与普通话共享请求路由，使用各自的发音资源和特征规则。参考录音转写按其声明的语言进入同一前端。

`frontend_python` 与 `acoustic_python` 分开表示工作进程角色。旧配置缺少 `frontend_python` 时继续复用声学解释器；发行 recipe 可让两种角色指向同一份 Python，以控制磁盘体积。Model 不再隐式绑定整合包路径，执行适配器根据当前安装清单绑定位置。

发行 recipe 记录目标平台、执行后端、语言、服务和工作进程位置。Windows 日英包与中日英包复用 CPU、CUDA 和 DirectML 运行环境，按语言配置装配前端程序和资源。Apple silicon 使用独立 MLX 组合。构建从明确指定的本地组件装配，HTTP 服务与准备组件可按用途选择。[发行组合](../../packaging/recipes)

校验放在拥有信息的边界：Model 检查描述和资源目录，后端与前端检查各自实际使用的模型及资源，构建检查发行文件闭包。共享入口不重复枚举 CUDA 的实验参数，也不重复判断已经由 Model 识别的格式。资源身份、文件范围、张量形状、IPC 长度和进程所有权仍影响正确性，继续保留。

## 当前范围与后续成本

`capabilities` 列出已实现的后端。源码安装列出所有已实现的语言，整合包列出随包提供的语言。实际可用性取决于设备、运行环境和当前模型的资源清单。HTTP 默认使用 direct 模式，所有后端遵循相同的请求互斥、取消和 managed 睡醒契约。[模型与功能验证矩阵](../specs/compatibility-matrix.md)

新增设备需要交付 GPT 与声学运行实现、模型转换适配、资源准备和目标系统的工作进程，再验证公开入口。新增语言需要在目标文本和参考转写两侧验证发音与特征，在混读时检查各段的音素对齐。最初的设备与前端职责核查见[源码核查记录](https://github.com/Rvosy/SakuraTTS/blob/main/research/notes/architecture-audit-20260922.md)，后续工作见[路线图](../roadmap.md)。

各后端共用 GPT-SoVITS 的权重与参考条件契约，转换器按执行格式导出 ONNX 图或 MLX 权重。发行包按各自包含的运行库和语言资源分别测量体积与性能。
