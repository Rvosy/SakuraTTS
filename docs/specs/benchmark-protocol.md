# 基准与验收协议

状态：设计草案；已有 [Mac 上游功能冒烟记录](../../research/experiments/2026-09-19-macos-reference-smoke.md)，尚未完成本协议规定的正式验收。更新日期：2026-09-19。

本协议用于验证 [推理契约](inference-contract.md)，同时比较安装体积、显存、速度和质量。作者公布的数据、公式估算和本项目实测分别标注。外部数据不能直接填入项目验收结果。

## 公平对照

首轮候选基线如下。路径无法运行或不兼容时记录原因，不能静默忽略。

| 路径 | 作用 |
|---|---|
| 官方普通推理路径 | 模型行为参考和现有执行方式对照 |
| 官方 CUDA Graph 路径 | 避免只与旧实现比较；仍需验证行为和模型兼容 |
| GSV-TTS-Lite，FlashAttention 关闭 / 开启 | 区分资源与执行安排的收益和额外注意力内核的收益 |
| SakuraTTS FP16 | 自有运行时的正确性及性能基线 |
| SakuraTTS 单项优化配置 | 测量执行图、采样、工作区或量化的净影响 |

Genie 的 CPU 路径只用于部署与阶段拆分参考，不纳入 GPU 加速比。已有 CPU TTS 方案不在本轮重新优化。

Mac 首轮使用 MPS / FP32，只覆盖官方普通路径和 Lite 非 Flash 路径。其重复次数、质量检查和内存测量不足以建立正式性能基线；CUDA Graph、CUDA FlashAttention 及原生 FP16 路径仍未验证。

所有 GPU 对照固定硬件、模型权重、参考音频、目标文本、语言处理能力、采样参数及语速。中文特征是否启用、执行设备和精度必须单列。减少模型功能、改变输出长度或改变采样条件的结果只能作为不同配置比较。

每个对照绑定准确仓库提交和环境，不使用只有名称的“Original”。记录实际运行的提交，不能把文档核对时的源码提交当作已执行的基准版本。

## 每次运行需要保存的信息

| 类别 | 内容 |
|---|---|
| 代码与环境 | 引擎提交、上游提交、构建方式、OS、CPU、RAM、GPU 型号与显存、驱动、运行库和算子库版本 |
| 模型 | 原始权重与模型包哈希、真实配置、图及转换器版本、精度、量化配置 |
| 输入 | 测试集版本、文本、语言、参考音频哈希、参考文本、预处理参数、参考缓存命中状态 |
| 执行 | 采样参数、随机种子及 RNG 实现、token 数、音频时长、停止原因、块长、前瞻、缓存容量、图捕获档位 |
| 并行负载 | 独占 GPU 或与桌宠渲染、本地语言模型共存；后台负载与 CPU 线程配置 |
| 结果 | 分阶段时间、首包和完成时间、内存数据、质量检查、错误与原始日志 |

按运行标识保存原始测量、配置、输出音频、对照结果和必要 profiler 轨迹。报告引用这些产物，不能只留下平均数或截图。模型权重和私有音频不随普通源码提交。

## 计量场景

| 场景 | 明确边界 |
|---|---|
| 首次安装与启动 | 无本引擎编译缓存，记录安装、依赖下载、首次编译和第一次可用音频 |
| 进程冷启动 | 新进程；分别说明磁盘编译缓存是否存在，模型尚未加载 |
| 模型已加载的首句 | 记录图预热是否发生；参考特征缓存命中与未命中分开 |
| 热推理 | 模型、参考条件及所需执行图就绪；不包含历史请求残留状态 |
| 连续流式生成 | 测量块间隔、队列峰值和欠载，包含长文本与容量边界 |
| 取消、重试和角色切换 | 覆盖 Prefill、Decode、音频生成、背压期间的取消及随后请求 |
| 加载、卸载和空闲恢复 | 比较模型常驻与卸载策略，检查资源是否随轮次增长 |
| 共存 | 使用同一输入，记录渲染和本地语言模型负载下的延迟与峰值 |

新进程不等于清空 OS 文件缓存，必须说明实际条件。不可把有磁盘缓存的启动标为完全首次启动。

## 速度指标

宿主提交完整请求的时刻记为 `t_submit`，首个非空、格式有效且可消费的 PCM 块到达宿主记为 `t_first_pcm`，最后有效音频和请求终态均交付完记为 `t_done`。计时不等待实际扬声器播放。

```text
首包延迟 TTFA = t_first_pcm - t_submit
请求完成时间 = t_done - t_submit
RTF = 请求完成时间 / 实际有效音频时长
```

冷启动另报告从启动进程到首个 PCM 的完整时间。流式结果记录首块时长与后续块间隔，防止通过发送极短块让首包数字变好，却无法持续播放。

分阶段记录文本前端、参考准备、Prefill、Decode、声学 / 波形生成和传输耗时。存在流水重叠时，各阶段时间之和不等于端到端时间；端到端使用主机单调时钟，GPU 子阶段使用对应设备计时并处理完成同步。

语义 token/s 只衡量语义生成，不能替代 TTFA 或 RTF。记录实际生成 token 数和停止原因；固定历史的单步测量与自然采样的端到端测量分别报告。

重复运行并保留每次数据，报告样本数、预热次数、p50、p95 和范围。样本不足时将分位数标为探索性结果。OOM、超时、取消或生成失败单独计数，不能从统计中消失。各实现轮换运行，减少温度、频率和后台负载漂移造成的偏差。

Profiler 会影响时序，性能数字取自独立正常运行，轨迹用于解释瓶颈。只在测量边界作必要同步，不为计时在产品解码循环中加入额外同步。

## 显存、主存与磁盘

显存至少观察：运行库初始化、模型加载、参考准备、图捕获 / 预热、首句、热推理、取消、卸载。分别报告进程占用、引擎分配数据与峰值，说明工具、采样频率和可能漏掉的瞬时峰值。

PyTorch 的 allocated / reserved 只能描述其分配器，不能代替整个进程的 GPU 占用。NVML、`nvidia-smi` 等在不同 OS / 驱动模式下的可见范围也需要说明；无法获取某项时标为不可用。报告进程绝对占用和相对空载增量，保留驱动上下文、第三方运行库和工作区成本。

不能把 KV 有效长度对应的字节数当作已经分配的全部容量，也不能把执行 Provider 的 arena 限制当作进程显存硬上限。主存同时记录进程常驻量及转换 / 首次加载峰值，避免把 GPU 内存压力无说明地转移到 RAM。

磁盘按下表计量，明确使用 MB / GB 还是 MiB / GiB，并保留原始字节数。

| 项目 | 必须包含的内容 |
|---|---|
| 下载体积 | 完成目标语言、角色推理所需全部下载；区分共享资源与角色增量 |
| 安装体积 | 引擎、必要运行库、语言资源、选定模型和参考条件 |
| 首次运行后体积 | 安装内容加编译、转换和其他必需缓存 |
| 新增角色的增量 | 新权重和参考条件，不重复计算真正共享的资源 |
| 转换与准备工具 | 单独计量工具、模型和临时文件；用户需要首次导入时列出额外需求 |

驱动可作为系统前置条件单列；所有必需依赖必须有归属。把大依赖改为首次启动下载，不能从总成本中扣除。压缩包大小不能代替安装后占用。

## 正确性与质量

验证顺序从确定性计算开始，避免随机生成差异掩盖算子错误。

| 层级 | 输入控制 | 检查内容 |
|---|---|---|
| 文本前端 | 固定文本、语言、词典和参考文本 | 规范化、音素、对齐、BERT 目标层及特殊 token 处理 |
| Prefill / 单步 Decode | 固定 token、特征、历史、位置和掩码 | KV 写入位置、有效长度、隐藏状态与 logits 的误差 |
| 采样 | 固定 logits、参数及可控随机输入 | 规则顺序、过滤集合、重复惩罚、EOS；跨 RNG 时另检验输出分布 |
| 声学与波形 | 固定语义 token、参考条件和噪声 | 中间特征、波形或频谱误差、输出长度、数值异常 |
| 端到端 | 相同测试集，多次自然采样 | 内容、音色、韵律、数字、混合语言、尾字、重复、异常停顿及提前结束 |
| 流式 | 与完整生成对照，管理重叠区噪声 | 接缝、重复播放、漏字、尾块、前瞻导致的内容变化和持续供音 |

数值报告包含绝对 / 相对误差及其分布，必要时查看 logits 排序差异。容差由模型、数据类型和参考实现的波动确定，在候选优化验收前固定，不能失败后临时放宽。

测试集至少覆盖中文数字、日期、多音字、短句、长句、标点、空输入、混合语言、不同参考音色，以及接近 token 容量的输入。只对宣称支持的语言给出通过结论，其他样例标为探索。

试听与客观检查并用：人工对照内容、音色、韵律和接缝；可用 ASR 内容错误率、说话人相似度及频谱指标辅助定位。单个客观分数不能替代听感，也不把小规模试听写成正式 MOS 研究。

量化使用独立于验收集的校准数据，保存校准版本。每个量化配置都与同模型 FP16 比较体积、时间、显存和质量，不继承其他模型或层的通过结果。

## 稳定性与干净部署

验证取消后重试、相同模型换参考条件、不同权重切换、连续加载卸载、缓存失效、输出背压和不支持的输入。检查旧请求音频、旧 KV 和失效图是否被错误复用，并观察内存是否随循环持续增长。

在目标系统的干净环境中安装运行包，使用已有受支持驱动和明确列出的运行依赖，完成文本到 PCM。验收环境不预装 PyTorch、训练工程或 CUDA 开发工具包。首次编译缓存与无缓存启动都需要覆盖。

GPU 失败不得用 CPU 推理结果冒充通过。宿主集成还需实际验证播放、取消和角色切换；独立 Harness 通过不等于桌宠集成通过。

## 验收预算与结果状态

性能阈值依赖目标设备和输入范围，目前没有足够信息填写。在 M0 完成时用基线确定性能预算和端到端质量标准；M1 建立中间结果对照时，再固定逐张量数值容差。两者均需在对应的候选实现验收前记录。

| 预算项 | 当前状态 | 固定时需要写明 |
|---|---|---|
| 安装及首次运行后体积 | 待定 | 目标语言、角色、完整依赖范围和上限 |
| 进程显存峰值与热推理占用 | 待定 | 目标 GPU、容量范围、测量工具及上限 |
| 热 TTFA p50 / p95、RTF | 待定 | 测试集、样本数、对照路径和上限 |
| 冷启动、取消延迟、队列容量 | 待定 | 实际启动条件、检查边界和上限 |
| 内容及听感要求 | 待 M0 固定 | 参考波动、质量评估方法与通过条件 |
| 逐张量数值容差 | 待 M1 固定 | 参考输出、数据类型、误差度量与允许范围 |

项目目标是同等能力下体积和显存下降、速度改善。若某项仅持平或退化，应说明取舍，不能概括为三项全部提升。所有阈值仍为空、缺少质量验证或缺少干净部署证据时，整体状态只能是未完成。

单项结果区分通过、失败和未验证；未运行、环境不支持、缺少样本都归入未验证并写明原因。报告同时保留官方与 Lite 的可比结果，不能只挑最慢的对照。
