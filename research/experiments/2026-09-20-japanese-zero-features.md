# 日文零特征只分配一次

日文 BERT 条件按固定官方规则全为零。`TextFrontend.segment` 原先为每个路由段分配一份 `(1024, phones)` FP32 数组，随后 `np.concatenate` 又分配完整数组。合并后的数组相同，前面的数组只增加临时空间。短音素需要重试时，首次分配也会被丢弃。

现在先合并音素、处理原有短音素重试，再一次分配最终零数组。仅接受日文路由的限制保持；空路由仍抛出 `ValueError`，非日文路由仍明确拒绝。最终特征依然是独立、可写、连续的 FP32 数组，形状和调用接口未改。没有裁剪中文 BERT，也没有把这个规则扩展到中文。

## 实测

证据位于 `SakuraTTS-References/runs/20260919T183342.366961Z-japanese-zero-features/`。目录保存前后源码、六条输入的完整特征、逐次计时、原始进程输出、CLI 命令和 WAV。基线为提交 `ed5b418`；原模型、词典、参考 A、seed 0 不变。原四条日文、换行三片及 550 字符两片的规范化文本、音素、segments、FP32 BERT 均相同，六个真实 CLI 进程退出 0，WAV 与上轮逐字节相同。

前端计时使用实际 G2P 和语言路由，加载后交替执行两种实现，各六次；测的是热前端，不含辅助模型加载、GPT 或声学生成。诊断另用 `tracemalloc` 记录 Python / NumPy 受跟踪分配，并排除在正常计时之外。

| 输入 | 原受跟踪分配峰值 | 修改后峰值 | 正常前端中位耗时，原 / 修改后 |
|---|---:|---:|---:|
| 原报告三句 | 477,757 B | 239,629 B | 0.339 / 0.337 ms |
| 原长句 | 2,193,859 B | 1,099,667 B | 1.422 / 1.380 ms |
| 换行三片 | 335,761 B | 240,993 B | 0.403 / 0.390 ms |
| 550 字符两片 | 9,081,899 B | 4,954,760 B | 7.045 / 7.064 ms |

长边界样例的峰值少 3.936 MiB；准备结果本身仍需相同的 4,915,200 B BERT 数组。计时差小，没有据此宣称速度改善。这些是受跟踪的分配字节，不能当作 RSS、MPS / MLX 或 NVIDIA 显存峰值；未宣称安装体积、GPU 占用或音质改善。

`boundary-check.py` 另核验空路由、英文路由、0 / 1 / 5 / 6 音素的重试和数组属性。首次临时检查误用了路由器接口，得到的两个 `TypeError` 比较不构成边界证据；原结果保留，纠正后的 `boundary-check-result.json` 明确记录这一点并通过六项检查。真实前端和 CLI 结果不受该临时检查错误影响。

## 复现与范围

`run.py` 保存输入、资源路径和全部 CLI 命令，`frontend-result.json` 保存逐次计时、诊断及源码哈希，`cli-result.json` 保存退出码和音频比较。复跑须将脚本、配置、原前端源码与输入清单复制到新目录，修改配置路径后使用日文环境执行；不要覆盖旧结果。边界检查使用同目录的 `boundary-check.py`。

这是删除重复分配，不是新的语音算法。有效改动保留；原概率 / MRTE 数值边界、新多片音频待试听、重复长句内容未验收及 Windows 未验证等状态，仍见[多片段记录](2026-09-20-japanese-multifragment.md)。
