# 日文多片段完整请求

## 问题与改动

官方 `cut0` 仍可能因换行或 510 字符规则得到多个片段。自有前端已经返回所有片段，但原合成入口要求恰好一片，导致这类请求无法生成。此次增加 `prepare_text_request`，CLI 一次准备全部文本，再逐片生成完整 WAV；原单片 Python API 保持严格拒绝多片，避免调用方无意中只处理第一片。

整条请求共用一个随机数状态。每片重新以参考和当前目标做 GPT Prefill，随后完成声学生成，再进入下一片；不在片间重设 seed，也不把所有 GPT 生成提前到声学之前。每片独立归一化、追加 0.3 秒静音。JSON 保留每片停止原因、PCM 偏移、长度和耗时；前端时间只记一次。

默认 staged 每片重新加载和卸载 GPT、SoVITS；simultaneous 在全部片段间复用权重，仍逐片释放 GPT 请求状态。某片达到次数限制后继续处理后文，完整请求退出 `2`。后片异常时不写 WAV，JSON 保留已完成片的信息和失败位置。

## 条件与证据

## 官方与自有对照

三行样例分成三片，采样步数为 22、43、38；550 字符样例为 `今日はいい天気ですね。` 重复 50 次，自动分成 506、44 字符两片，音素数为 1104、96，采样步数为 509、202。后者专门检查分割边界，不替代原始回归文本，也不据此判断长文内容完整。

共五片、814 步通过以下检查：原文独立准备所得的规范化文本、音素和 BERT；参考五数组；真实生成 token、各步历史、停止原因和语义切片；独立固定官方历史下的 logits；相同历史下的采样概率与筛选集合；最终波形。logits / 波形使用既有 `atol=1e-4, rtol=1e-5`，概率使用 `atol=1e-6, rtol=1e-5`，没有放宽容差。第一片、第二片可以有不同停止原因，不从最后一片复制结论。

逐片官方波形按原规则后处理后，与官方完整 PCM 逐字节相同。自有最终波形通过容差，但 PCM 不是逐字节相同：三片请求的 156,800 个采样中有 912 个相差 1 个整数刻度；长请求的 926,720 个采样中有 7,336 个相差 1 个刻度。未另设宽松 PCM 阈值，也未把整数差小等同于音质通过。后续 ASR 另见下文，人工试听尚未验收。

长样例必须显式增加容量；其首片文本加参考前缀已经超过默认 1024。4096 只属于本次验证配置，不自动作为所有请求的默认值。这些检查不包含全套声学中间阶段重验，此前概率 / MRTE 失败样例仍保留。

## CLI 回归与速度、资源

十个真实 CLI 进程的检查全部通过：原四条单片的文本、生成摘要和 WAV 与既有 seed 0 基线相同；新增三片请求在 staged、simultaneous、staged + 绑定参考下的 WAV 相同。三片各生成 36、50、38 个采样 token。把 `early_stop_num` 设为 10 时，三片均在第 11 个采样后结束，完成后退出 `2`。用容量 256 运行短首片、长后片时，首片完成、第二片明确报容量错误，未写出部分 WAV。短行合并样例仍得到官方规定的一片。

另三个最终源码 CLI 进程补验：`all_ja` 的三片 WAV 与同输入 `ja` 相同；550 字符输入在容量 4096 下生成两片，分别采样 531、184 步；默认容量 1024 在首片明确失败，未写 WAV。这是参考 A / NumPy seed 0 的独立生成，不与参考 B / 官方随机数的步数混比。13 个进程包含两种预期错误和一次限额退出，并非 13 次正常合成。

性能样例为 `こんにちは。\n今日はいい天気ですね。\nよろしくお願いします。`，其中 `\n` 在实际输入中为换行。有效波形 4.84 秒，另有三段各 0.3 秒尾静音。每种策略在一个新进程内先执行一次，再执行三次热请求；各请求仍按所选策略加载、释放模型。计时未加入诊断插桩。进程冷启动另存，不用首个请求时间代替整进程启动。

| 指标 | staged | simultaneous |
|---|---:|---:|
| 首次完整请求 | 2.762 s | 1.860 s |
| 三次热请求中位数 | 2.649 s | 1.768 s |
| 热请求 RTF，分母不含尾静音 | 0.547 | 0.365 |
| 独立诊断的 MLX 分配器高水位 | 417.15 MiB | 627.21 MiB |
| 诊断进程生命周期 RSS 高水位 | 652.97 MiB | 866.14 MiB |
| 诊断结束 RSS 边界 | 368.09 MiB | 654.63 MiB |

本例 staged 分配器高水位少约 210 MiB，热请求多约 0.88 秒，重复加载成本明显。保留两种策略，不自动用低内存配置替用户决定延迟取舍。诊断运行在请求前清空空闲缓存并重置 MLX 高水位，含整个 CLI run；两次结束 active/cache 均为零，但 RSS 仍有驻留。上述单次诊断及边界不能当作长期泄漏结论，也不能推为 NVIDIA 显存。诊断时间不进入正常耗时统计。

## 复现

官方捕获使用开发环境，从真实原始参考准备元数据起步：

```sh
SAKURA_REFS=../SakuraTTS-References
"$SAKURA_REFS/.venv-official-macos/bin/python" -B research/tools/official_multifragment_capture.py \
  --prepare-inputs "$SAKURA_REFS/runs/20260919T154608.547186Z-official-reference-capture/reference-inputs.json" \
  --references "$SAKURA_REFS" --seed 1234 \
  --text 'こんにちは。
今日はいい天気ですね。
よろしくお願いします。'
```

CLI 套件的 `run.py` 保存全部命令。普通模式执行十个回归；`--performance` 分别运行正常计时和诊断进程。复跑须复制脚本、配置和冻结源码到新目录并更新 `config.json` 的 `run`，避免覆盖既有文件。原四条基线来自 `20260919T174317Z-japanese-runtime-relocation/baseline/`；同 seed 只用于自有运行时回归，不视为 Torch 等价 RNG。

自有固定随机数对照使用 `research/tools/native_multifragment_replay.py`，传入 `--official-run`、四个 `--*-package` 和 `--references`。本轮 reference 包为 `20260919T152440.202799Z-v2pro-japanese-reference`；长样例另加 `--capacity 4096`。每个结果目录的 `prepared.json` 保存完整绝对路径命令、依赖版本和哈希，`process-result.json` 保存实际退出码。概率失败会保留 `numerical_mismatch`，不会因 token 相同而算通过。

## 独立内容检查

使用已有离线 `mlx-community/whisper-small-mlx`，固定提交 `45f3915923c7a79a5a5b5a7d909d39aeb0e5630e`，不提供目标转录提示。官方三片、自有固定随机数三片、CLI 自由生成三片的转写都包含 `こんにちは`、`今日はいい天気ですね` 和 `よろしくお願いします`。这补充了内容识别证据，不能验证助词实际读音、音色和自然度。

550 字符重复句样例的官方与自有音频均只被 ASR 转写为一次 `今日は良い天気ですね。`。该结果不能证明 50 次重复被完整读出，也不足以区分识别器压缩重复与 TTS 内容缺失；保留为未通过完整内容验收的边界样例，不用它评价长文语音质量。没有修改输入来换取识别通过。

## 范围

此次支持完整离线 WAV，没有实现流式首包或 CLI 取消协议。新多片样音的人工试听待反馈，不继承此前指定文件的听感结论。510 字符切分不保证 KV 或位置容量足够，也不证明长文能被模型完整念出。原部署目录仍为旧源码，本轮源码变化不自动计入此前 1.047 GiB 隔离验收。
