# MLX 中文 BERT 特征转换与对照

日期：2026-09-19。设备：Apple M4、16 GB 统一内存。状态：真实模型的 CPU 对照通过，GPU 逐层对照有 1 个超限元素，完整语音链路尚未接入。

## 改动与验证范围

`src/sakuratts/backends/mlx/bert.py` 实现 FP32 中文 BERT 特征计算，运行时只导入 MLX、NumPy 和标准库。转换器仍使用 PyTorch / Transformers，输出新模型包，不覆盖官方权重。

实际模型是 `chinese-roberta-wwm-ext-large`，24 层、隐藏维度 1024、16 个注意力头、FFN 维度 4096。官方选取 `hidden_states[-3]`，因此保留 embedding 和前 22 层，删除后两层和 MLM head，不加载 pooler。该裁剪沿用已完成的 [BERT 依赖裁剪对照](2026-09-19-bert-and-reference-memory.md)。词元化、CLS / SEP 去除和 `word2ph` 展开保留在模型外部。

运行时保留绝对位置、token type、非因果注意力、key padding mask、残差和 post LayerNorm。GELU 使用 `erf` 公式。模型包保存 FP32 权重、配置、原文件哈希和包哈希；没有量化或近似激活选项。

## 证据

产物均在参考目录的 `runs/` 下，包含逐层数组、输入来源、转换命令、模型包及代码快照：

| 运行目录 | 内容 | 结果 |
|---|---|---|
| `20260919T112244.959514Z-mlx-bert-cpu` | 合成 6→4 层模型，普通输入、padding / token type、显式位置 ID 共 3 例 | CPU 全层通过，最大绝对误差 `7.153e-7` |
| `20260919T112854.850786Z-mlx-bert-cpu` | 真实 24→22 层模型，5 段官方规范化中文 | CPU 全部通过；GPU 有 1 个逐层超限元素 |
| `20260919T113917.767880Z-bert-layer-diagnostic` | 第 18 层固定输入及独立算子对照 | GPU 所有局部检查通过；上游输入差异解释该坐标的大部分偏差 |
| `20260919T113948.078408Z-mlx-bert-layer-refactor` | 提取单层执行入口后的全模型回归 | CPU / GPU 各自与修改前的全部保存数组逐位相同 |

真实输入取自已保存的官方 trace：固定中文回归句、中文长句、复杂标点句，以及中英混合样例的两段中文。沿用原始规范化文本、音素和 `word2ph`，未改写输入。5 段特征分别展开为 56、200、57、14、17 个音素。

转换按顺序执行：先保存完整模型的 embedding 和前 22 层结果，释放完整模型，再加载裁剪模型。5 段裁剪结果都与完整模型逐位相同。转换使用 2 个 PyTorch CPU 线程，同一时刻只保留一份大 BERT。

验证环境为 MLX 0.32.2、NumPy 2.4.6，未安装 PyTorch / Transformers。CPU 和 GPU 报告都记录 `runtime_imported_torch=false`、`runtime_imported_transformers=false`。每个设备单独保存报告和数组，GPU 验证未覆盖 CPU 结果或转换清单。

## 真实模型数值结果

运行前固定比较容差为 `rtol=1e-4, atol=1e-5`。每段比较 embedding、22 个编码层及音素展开结果，共 24 项；5 段共 120 项。

| 设备 | 逐层及音素检查 | 所有张量最大绝对误差 | 最终特征及音素展开 |
|---|---:|---:|---|
| MLX CPU | 120 / 120 通过 | `1.23978e-5` | 5 / 5 通过 |
| MLX GPU | 119 / 120 通过 | `4.95911e-5` | 5 / 5 通过 |

唯一失败在固定中文样例的 `layer_18`，即 `encoder.layer.17` 输出。该张量形状为 `[1,32,1024]`，32,768 个元素中只有坐标 `[0,22,708]` 超限：

| 项目 | 值 |
|---|---:|
| 官方 CPU FP32 | `-0.0005522239953279495` |
| MLX GPU FP32 | `-0.000564496498554945` |
| MLX CPU FP32 | `-0.0005516763776540756` |
| GPU 绝对误差 | `1.2272503226995468e-5` |
| 该坐标允许误差 | `1.0055222446681e-5` |

GPU 整体状态保留为 `numerical_mismatch`，不因最终层通过而改成通过。离线定位保存在 `gpu-mismatch-analysis.json`。

### 固定输入的单层诊断

`research/tools/bert_layer_diagnostic.py` 只加载 `encoder.layer.17`，分别输入已保存的官方第 17 层结果和 MLX GPU 第 17 层结果。两套输入各自经过官方 CPU 和实际 MLX GPU 单层实现，再比较 attention、LayerNorm、GELU 和线性层。独立算子对照则给每个算子直接输入它在官方路径中的输入值，排除之前计算的误差。

官方 CPU 单层从官方输入精确复现原始第 18 层输出。两套输入的 MLX GPU 单层及独立算子检查全部通过原容差。失败坐标的值如下：

| 层输入与执行后端 | 输出值 |
|---|---:|
| 官方输入 → 官方 CPU | `-0.0005522239953279495` |
| 官方输入 → MLX GPU | `-0.0005530709167942405` |
| MLX GPU 输入 → 官方 CPU | `-0.0005631707608699799` |
| MLX GPU 输入 → MLX GPU | `-0.000564496498554945` |

在这个坐标，单独把层输入换成 MLX GPU 的结果，官方 CPU 输出就偏移了约 `1.09468e-5`；在这个相同输入上，再换成 MLX GPU 单层计算，额外偏移约 `1.32574e-6`。GPU 单层回放与原完整链路的第 18 层张量逐位相同，确认诊断确实复现了原计算。

这说明该超限点的大部分差异已经随上游输入进入第 18 层。当前证据不支持把问题归因于这一层的单个 attention 或 LayerNorm 算子，也没有据此改变全链路容差。更早的误差来源仍待逐层定位。

为复用实际运行代码，运行时新增 `encoder_layer()` 入口，将原循环体原样提取。5 段全模型 CPU / GPU 回归中，embedding、所有层和音素特征均与修改前各自的数组逐位相同。CPU 仍全部通过，GPU 仍是上述唯一失败。

## 体积与边界

转换包包含 299,280,384 个 FP32 参数、357 个张量。`weights.npz` 为 1,197,233,952 字节，约 1,141.77 MiB。此数字是模型文件大小，不能当作 GPU 占用，也不能直接与其他存储精度的原始文件比较。

逐层捕获包含诊断保存和额外中间张量，报告中的 `seconds_including_diagnostics` 不用于正常性能结论。正常 CPU 计时和资源对照见下一节；GPU 正常计时和资源仍未验证。

独立 `tokenizers` 直接读取原 `tokenizer.json`，在 10 条原始回归文本和 5 段规范化文本上，与 `AutoTokenizer` 的 ID、token type 和 attention mask 完全一致。这仅验证词元化资源加载，不代表中文 G2P 已脱离 PyTorch / Transformers，也不是全部语言兼容结论。

本轮没有生成新音频，没有 ASR 或人工试听结果。中文和日文用户报告继续沿用各自的语音回归状态。

## 正常 CPU 速度与资源对照

`research/tools/bert_cpu_benchmark.py` 比较同样的 22 层 FP32 计算，两后端各启动一个新进程，顺序运行。5 段输入沿用上面的官方 token 数组。每段先验证最终特征和音素展开，再做 2 次预热、5 次热运行。计时只包含已词元化输入到最终特征；不捕获中间层，不包含 NumPy 复制、音素展开、比较、文件写入或内存查询。MLX 在返回前执行 `eval`，未只测异步提交时间。

记录位于参考目录：

- PyTorch：`runs/20260919T115204.906943Z-bert-cpu-torch-benchmark`。
- MLX：`runs/20260919T115225.054226Z-bert-cpu-mlx-benchmark`。
- 离线汇总：`runs/20260919T115403.411348Z-bert-cpu-comparison`。

所有数值检查通过。PyTorch 最终输出与官方 gold 逐位相同；MLX 最大绝对误差为 `1.23978e-5`，满足预设容差。运行时仍未导入 PyTorch 或 Transformers。

| 输入 | PyTorch 中位数 | MLX 中位数 | 本轮 MLX 用时变化 |
|---|---:|---:|---:|
| 固定中文回归句，32 token | 42.25 ms | 45.17 ms | +6.91% |
| 中文长句，106 token | 99.74 ms | 99.39 ms | -0.35% |
| 复杂标点，34 token | 53.73 ms | 56.23 ms | +4.65% |
| 混合文本中文开头，10 token | 40.61 ms | 41.49 ms | +2.19% |
| 混合文本中文结尾，11 token | 40.89 ms | 41.88 ms | +2.40% |

MLX 在本轮 4 个短样例上慢约 2%–7%，长句基本持平。这组结果支持 CPU 辅助 BERT 作为可继续集成的准确路径，不支持“更换后端即提速”的结论。5 次运行不足以建立稳定的延迟分位数或统计显著性。

| 资源或加载阶段 | PyTorch | MLX |
|---|---:|---:|
| 数值库导入 | 2.528 s | 0.044 s |
| 校验文件并加载模型 | 0.508 s | 0.675 s |
| 加载前 RSS | 357.88 MiB | 45.59 MiB |
| 加载后 RSS | 1554.97 MiB | 1420.50 MiB |
| 热运行结束、保留模型的 RSS | 1564.77 MiB | 1456.00 MiB |
| OS 记录的进程全生命周期 peak RSS | 2125.92 MiB | 1456.03 MiB |
| 删除模型并 GC 后的 RSS | 896.97 MiB | 1456.02 MiB |
| 再清理 MLX 缓存后的 RSS | 不适用 | 291.98 MiB |

同样保留 22 层权重时，MLX 空闲 RSS 少 108.77 MiB（6.95%）。进程全生命周期 peak RSS 少 669.89 MiB（31.51%），但该高水位包含导入、加载及验证，不能称作生成阶段峰值。边界 RSS 也不是瞬时峰值，更不是 NVIDIA 显存。

MLX 删除模型后仍由分配器保留缓存；`mx.clear_cache()` 后 RSS 降至 291.98 MiB。调用方需要把删除引用和释放缓存纳入卸载流程。PyTorch CPU 删除和 GC 后仍有 896.97 MiB RSS，此处没有把它诊断为泄漏，也没有尝试系统分配器专用释放操作。两条路径的卸载结果按实际动作分别记录。

加载数据受格式差异影响：PyTorch 读取原始 `pytorch_model.bin` 并加载为 22 层 FP32；MLX 读取转换后的 FP32 NPZ。两侧加载区间均包含文件完整性校验，MLX 包更大、校验和加载更慢。两次进程启动未清理 OS 文件缓存，因此上表不能当作断电冷启动或干净安装结论。

导入数值库前，两个进程都设置 `VECLIB_MAXIMUM_THREADS`、`OMP_NUM_THREADS`、`OPENBLAS_NUM_THREADS`、`MKL_NUM_THREADS` 为 2。PyTorch 另设 intra-op 为 2、inter-op 为 1，并保存 `parallel_info()`。MLX 0.32.2 没有公开的独立 CPU 线程计数接口，所以这里只声称使用同样的 BLAS 线程限制，未断言内核实际线程数完全相同。每次运行也保存进程 CPU 时间；MLX 各段 CPU / wall 中位比为 1.03–1.07，PyTorch 为 1.02–1.14。

测量时其他项目推理任务已暂停，普通桌面负载和 OS 文件缓存没有控制。没有新音频、ASR 或听感结论，也未测 tokenizer / G2P 或整条 TTS 延迟。
