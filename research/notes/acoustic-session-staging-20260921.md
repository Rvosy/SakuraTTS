# 声学 Session 错峰加载实测

日期：2026-09-21。基线：`f302aa2696ceb27c1855e30346f32606431c36bd`。设备仍为 RTX 5060 8 GB、Windows 11 WDDM、驱动 610.62；模型为 Sakura V2ProPlus，双 FP16、chunk256、capacity=2048。

本轮实现了 latent 与 vocoder Session 错峰加载。低显存档的完整请求观测峰值从 **758.2 MB 降到 584.1 MB**，空闲从 **569.4 MB 降到 387.0 MB**；极限档峰值从 **498.1 MB 降到 465.1 MB**，空闲保持 **106.5 MB**。主对照四组共 48 次请求完成，对应音频逐采样一致。

随后复用已有的 Prefill query128 分块，另测 12 次请求，组合峰值进一步降到 **416.8 MB**，空闲仍为 **106.5 MB**。这组长句的生成结果会改变，保留为需要试听验收的独立实验档。

全文表格使用十进制 MB：1 MB = 1,000,000 字节。原始记录保留 MiB，1 MiB = 1.048576 MB。这里的占用是同一时刻、同一适配器上的实验主进程与声学 worker 的 WDDM Dedicated Usage 之和，不是独占物理显存保证。

## 峰值显存

| 配置 | 本轮原配置复测 | 加入声学错峰 | 本轮再节省 |
|---|---:|---:|---:|
| FP16 低显存档，release-state | 758.2 MB | **584.1 MB** | **23.0%** |
| FP16 极限档，staged | 498.1 MB | **465.1 MB** | **6.6%** |

对应原始读数分别为 723.043 → 557.043 MiB、475.043 → 443.527 MiB。两条原配置都复现了上一轮的完整峰值。

## 空闲显存

| 配置 | 本轮原配置复测 | 加入声学错峰 | 本轮再节省 |
|---|---:|---:|---:|
| FP16 低显存档，release-state | 569.4 MB | **387.0 MB** | **32.0%** |
| FP16 极限档，staged | 106.5 MB | **106.5 MB** | 0.0% |

空闲取最后一次请求完成后约 1 秒内的稳定中位数。低显存档保留 GPT 权重和声学 worker，但卸载声学 Session；极限档还会关闭 GPT 和声学 worker，因此本轮没有再降低它的空闲占用。

沿用[上一轮原版 FP16 对照](low-vram-20260921.md)的 2323.2 MB 峰值、1677.2 MB 空闲，新低显存档分别减少 74.9% 和 76.9%，新极限档分别减少 80.0% 和 93.7%。原版没有在本轮重跑，这些是跨轮次参考；上面两张表才是本轮只改变声学生命周期的直接对照。FP32 本轮未改，也未重测。

## 改了什么

新增实验选项 `acoustic_session_policy="staged"`，默认仍为 `"resident"`。原路径在加载声学模型时同时创建两张 Session；新路径在每个片段中依次执行：

1. 加载 latent Session，保留 encoder／flow 的完整上下文，得到完整 CPU latent。
2. 释放 latent Session，再加载一次 vocoder Session。
3. 处理该片段全部 256 帧声码器块，拼回完整波形，再释放 vocoder Session。

没有改模型图、精度、块长、KV 容量、生成上限、噪声消费顺序或波形归一化，也没有量化。vocoding 不会每块重建 Session。这个选项仅允许已通过原有筛查的分块声学包，不能直接用于完整声学图。

私有 worker 的 `ready` 记录增加 `session_initialization`：新策略为 `deferred`，此时只是进程和模型包已准备，CUDA Session 尚未创建。每张 Session 真正建立时仍校验 CUDA provider 和输入输出结构，父进程也核对策略与初始化状态。

失败清理覆盖构造、schema、执行和无效输出。ORT 可能把失败 Session 留在异常的 cause/context 链中，本轮清理完整异常链的局部引用，避免调用方保留异常对象时继续占用显存。开发用的既有 Session adapter 也同步适配；默认 resident 的计算逻辑保留。

## 峰值已经转到哪里

现有 WDDM 工具新增 `--profile-stages`。主进程记录 GPT 加载、Prefill、Decode＋采样和释放；声学 worker 返回 Session 创建、执行、释放的 wall-clock 区间。分析仍汇总同一采样时刻的进程计数，不把不同时间的模块峰值相加。

| 极限档内部阶段 | 两张声学 Session 常驻 | 声学 Session 错峰 |
|---|---:|---:|
| GPT Prefill／Decode＋采样 | 465.1 MB | 465.1 MB |
| latent 执行 | 491.8 MB | 401.6 MB |
| vocoder 执行 | 498.1 MB | 414.2 MB |
| 完整流程最高点 | 498.1 MB | **465.1 MB** |

声学内部的显存重叠确实消除了，但总峰值只下降 33.0 MB，因为 GPT 成为新的最高点。在此配置下，继续缩小声码器块或削减声学参考投影权重，不能直接降低极限档的整体峰值。因此本轮追加了下面这组 GPT 分块对照。

## Prefill 分块现在有了组合收益

已有的 `gpt_prefill_query_chunk_size=128` 曾在上一轮保持 475 MiB 总峰值不变，因为当时最高点在声学。声学错峰后重新测量，得到：

| 阶段 | 声学错峰，完整 Prefill | 声学错峰＋Prefill query128 |
|---|---:|---:|
| GPT Prefill／Decode＋采样 | 465.1 MB | 416.8 MB |
| latent 执行 | 401.6 MB | 410.0 MB |
| vocoder 执行 | 414.2 MB | 414.2 MB |
| 完整流程最高点 | 465.1 MB | **416.8 MB** |

组合的原始峰值为 397.527 MiB，比原极限档 498.1 MB 再省 **16.3%**；相对只做声学错峰的 465.1 MB，再省 **10.4%**。请求后的空闲仍是 106.5 MB。峰值由 GPT 决定，但它已经非常接近声学的 414.2 MB，继续优化时需要同时看两边。

这组 12 次请求全部完成；长句语义 token 从 629 变为 640，扩展长句从 844 变为 859，4 条对应 PCM 改变，其余 8 条不变。新增的声学错峰没有再引入差异：与上一轮已经生成的 `fp16-staged-q128` 相比，12 条 PCM 全部逐位一致。不能把这解释成与原 FP16 音质相同，或已完成人工内容验收。

组合档的热短句、长句、扩展长句耗时中位数分别为 2.856、5.591、6.976 秒；后两类输出长度已经变化，不能据此做固定工作量的速度比较。新进程至首份完整 PCM 为 5.494 秒，仍为单次带缓存的观测。

## 延迟代价

下表为持续显存采样时的完整请求耗时中位数。热短句 n=3，长句与扩展长句各 n=2；长句生成 25.46 秒音频，扩展长句 34.06 秒。样本量较小，不能当作稳定的性能排名。

| 配置 | 热短句 | 热长句 | 热扩展长句 |
|---|---:|---:|---:|
| 原低显存档 | 0.234 s | 2.677 s | 4.135 s |
| 低显存档＋声学错峰 | 1.009 s | 3.560 s | 4.964 s |
| 原极限档 | 3.101 s | 5.460 s | 6.993 s |
| 极限档＋声学错峰 | 3.055 s | 5.481 s | 6.896 s |

低显存档以前复用两张 Session，新策略每片段重建，约增加 0.8 秒；极限档原本每片段都重建，因此本轮耗时接近。它仍保留每请求约 3 秒的加载成本，没有被本次优化消除。

新极限档的阶段计时进一步说明了成本组成：GPT 加载中位数 679 ms，声学 worker 启动与包校验 603 ms，latent Session 创建 774 ms，vocoder Session 创建 88 ms，声学 worker 退出 163 ms。各阶段中位数不能简单相加当成某一次完整请求，GPT 加载也尚未细分文件哈希、NPZ 解码、精度转换和上传。

从新进程启动到第一份完整 PCM，原低显存／新低显存分别约 4.924／4.928 秒，原极限／新极限约 6.547／5.692 秒。这是各一次带采样的观测，磁盘和编译缓存未清空，不代表首次安装或稳定冷启动加速。

## 使用方式

本轮测过的三个候选后来按[四档方案](../../docs/inference-profiles.md)整理，配置位置如下：

- [FP16 低显存，E 档](../../examples/low-vram.json)：584.1 MB，接受每片段多约 0.8 秒。原文件名为 `low-vram-acoustic-staged.json`。
- [FP16 极限，H 档](../../examples/minimum-vram.json)：465.1 MB，主对照音频逐位一致，延迟接近原极限档。原文件名为 `minimum-vram-acoustic-staged.json`。
- [声学错峰＋Prefill query128 研究配置](../experiments/configs/fp16-staged-acoustics-prefill128.json)：416.8 MB，部分长句生成结果改变，需单独试听验收。该组合仅保留为研究记录，不作为当前档位提供。

它们需要已有的 FP16 chunk256 模型包，不会自动转换普通 FP32 模型。本机复现 465.1 MB 档的入口为：

```powershell
.venv-windows-runtime/Scripts/python.exe -m sakuratts tts `
  outputs/low-vram-20260921/fp16.json `
  --experimental examples/minimum-vram.json `
  --text "おはよう。今日もよろしくね。" --split-method cut0 `
  --output outputs/minimum-acoustic-staged.wav
```

HTTP 仍不支持总体 `policy="staged"`；极限档使用公开 Python `Engine` 或 `tts` CLI。低显存候选可经 `serve --experimental` 传入，本轮资源测量使用公开 `Engine`，未重测 HTTP 峰值。按标点分句要显式用 `cut5`，会增加片段数和重载次数；本表最低数字来自 `cut0`。

## 验证与限制

四组主对照按顺序独立启动，均执行短句、长句、多句、标点、扩展长句、短句，两轮共 12 次。参考音色为中性，seed=1234，GPT 和声学 FP16、CUDA Graph、arena 回收及 chunk256 一致；主对照关闭 Prefill query 分块。追加的 query128 组合采用相同请求序列，总共五组、60 次资源测量请求。

- 48 次请求全部完成，48 份 WAV 的帧数和 PCM SHA-256 与报告一致；四组两两对应的 12 条 PCM 均逐位相同，语义序列、参数和参考身份也一致。
- 追加 query128 的 12 次请求与 WAV 校验全部通过，差异按上文单独记录，没有合并进 48 条主对照的等值结论。
- 补测中性→惊讶→中性与 7 片段 `cut5` 长句；两种声学策略的四对输出完全相同，中性切回也恢复相同 PCM。未改变 RNG 消费顺序。
- 真实 GPU 生命周期检查的 6 个场景通过，覆盖自有空闲 worker 退出后的恢复、显式卸载、取消后重试；复放 PCM 完全相同，所持有进程正常退出。没有测试计算中途强杀或取消响应时间。
- 全套单元测试共 347 项，345 项通过、2 项跳过；`git diff --check` 通过。新极限档 JSON 已经实际 `tts` CLI 生成完整 WAV，PCM 与对应测量短句一致。
- 源文件在资源测量期间未改变；采样中位数约 20 ms，最大间隔为 41.7–88.1 ms，仍可能遗漏更短尖峰。阶段中没有采到数据的区间保持为空，没有当作零。
- Shared Usage 峰值约 165.7 MB，单独记录为系统内存；不混入上面的 Dedicated 表，也不把 Total Committed 当作物理显存。

本轮没有人工盲听，PCM 一致只能证明此次生命周期调整在这些输入上没有新增音频差异。原有长句与标点内容验收问题仍保留。也没有验证陌生参考首次准备、任意长度输入、并发、长时间驻留或实际 1 GB 显卡。

原始 WDDM 样本、逐请求报告、阶段时间、样音与环境保留在 `outputs/acoustic-staging-20260921/`；[仓库内汇总数据](../experiments/data/2026-09-21-acoustic-session-staging.json)保存峰值、时长、配对、源指纹和文件哈希。

## 下一步

未开启 Prefill query 分块时，GPT 从只加载权重的 265.8 MB 增至执行时 465.1 MB。其中固定 KV 可直接核算为 `2 × 24 × 16 × 2048 × 32 × 2` 字节，即 100.66 MB；Decode 显式工作区与状态仅约 0.015 MB。最高样本落在扩展长句的 Prefill，该请求前缀长度 644，单份 FP32 分数矩阵为 26.54 MB，掩码替换时旧、新矩阵可能同时存活。以上解释了主要分配对象，不能把各算子的临时峰值全部相加，或把未解释部分都归因于 CUDA Graph。

保持完整 Prefill GEMM 形状时，可以先验证分数缓冲复用与原位掩码，争取继续减少显存而不改变数值路径。按需 KV 也有空间，但增长时的旧、新缓存重叠和 Graph 重捕获必须测量；不能直接降低容量或截短输入来兑现节省。仅在 Prefill 之后清内存池，无法消除已经出现的 Prefill 峰值。

要减少极限档重载时间，可复用已验证、绑定模型身份与精度的 CPU 权重快照。当前 FP16 数组约需 159.31 MB 主存，可能减少重复文件校验、解码和转换，但不是额外显存收益。声学 worker 常驻也需单独测量，防止它的 CUDA 上下文重新抬高 GPT 峰值。

附件提到的参考投影裁减有明确对象：本地 Windows FP16 图中，四组 flow 条件参数共 12.60 MB，vocoder 条件参数 1.57 MB，投影结果仅约 0.014 MB。Windows 已折叠 WeightNorm，不能套用 Mac 参数库存；迁移还需处理 V2ProPlus 接口、FP16 计算顺序和参考切换。它可能帮助低显存档的声学阶段。对 416.8 MB 组合档，GPT 与声学已经接近，下一轮可在 GPT 缓冲优化后重新评估这项裁减，不预先承诺两边参数节省能直接相加。
