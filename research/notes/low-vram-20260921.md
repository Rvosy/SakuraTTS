# SakuraTTS 低显存实测与低配版本建议

日期：2026-09-21。设备：RTX 5060 8 GB，Windows 11 WDDM，驱动 610.62。模型：Sakura V2ProPlus，日文，单请求。

后续[声学 Session 错峰实验](acoustic-session-staging-20260921.md)已将低显存档峰值进一步降到 584.1 MB、极限档降到 465.1 MB；另测 Prefill query128 组合为 416.8 MB，但部分长句生成结果改变。下文保留本轮原配置和原始测量口径。

**在本轮测试范围内，完整推理的观测峰值已经低于 1 GiB。** 双 FP16、256 帧声码器分块、释放 GPT 请求状态时为 **723.0 MiB**；GPT 与声学模型分阶段加载时为 **475.0 MiB**。加入按标点分句的低显存档为 **665.0 MiB**，但它改变了执行方式，单独列组。

当前 FP32 默认路径的观测峰值是 **2049.1 MiB**，比同轮原版 FP32 少 **1700.5 MiB，降低 45.4%**。FP16 低显存档比原版 FP16 少 **1492.5 MiB，降低 67.4%**；极限档少 **1740.5 MiB，降低 78.6%**。

峰值与空闲对照如下，各行与同精度原版比较。此表按十进制 MB 换算（1 MB = 1,000,000 字节，1 MiB = 1.048576 MB），后文详细测量表保留 MiB：

| 配置 | 原版峰值 | SakuraTTS 峰值 | 峰值节省 | 原版空闲 | SakuraTTS 空闲 | 空闲节省 |
|---|---:|---:|---:|---:|---:|---:|
| FP32 | 3931.7 MB | 2148.6 MB | 45.4% | 3076.0 MB | 1253.1 MB | 59.3% |
| FP16 低显存档 | 2323.2 MB | **758.2 MB** | **67.4%** | 1677.2 MB | **569.4 MB** | **66.0%** |
| FP16 极限档 | 2323.2 MB | **498.1 MB** | **78.6%** | 1677.2 MB | **106.5 MB** | **93.7%** |

空闲取最后一次请求结束后约 1 秒的稳定值；极限档此时已卸载 GPT 和声学模型，下一次请求需要重新加载。计数包含驱动和运行库保留的分配。

建议先提供可选的 FP16 低显存实验档，长文本显式使用分句。极限档可留给显存更紧张、能够接受每次多等约 3 秒的用户。当前证据还不足以承诺“任意输入、任意 1 GB 显卡都能运行”，音质也尚未完成主观验收。

## 同口径对照

每组使用独立新进程，依次执行短句、长句、多句、标点、扩展长句、短句，共两轮、12 次请求。输入文本、模型权重、参考音频和采样参数一致。原版与 SakuraTTS 的随机数实现不同，因此生成 token 和音频长度允许不同；这是相同应用请求的资源对照，不是固定工作量的算子比较。

下表全部使用 Windows PDH `GPU Process Memory / Dedicated Usage`。SakuraTTS 取同一时刻、同一物理适配器上的主进程与声学 worker 之和。单位均为 MiB。

| 路径 | 冷启动至首句峰值 | 全流程峰值 | 最后请求后空闲 | 相对同精度原版的峰值降幅 |
|---|---:|---:|---:|---:|
| 原版普通推理 FP32 | 3099.5 | 3749.5 | 2933.5 | — |
| SakuraTTS FP32，当前默认回收 | 1117.1 | 2049.1 | 1195.1 | 45.4% |
| 原版普通推理 FP16 | 1941.5 | 2215.5 | 1599.5 | — |
| SakuraTTS 双 FP16，分块、常驻 | 713.0 | 865.0 | 763.0 | 61.0% |
| 双 FP16，分块、释放请求状态 | 635.0 | 723.0 | 543.0 | 67.4% |
| 双 FP16，分块、分阶段加载 | 437.0 | 475.0 | 101.5 | 78.6% |
| 分阶段加载，再加 Prefill query 分块 | 437.0 | 475.0 | 101.5 | 78.6%，未再降低峰值 |

原版 FP16 采用补跑结果。首轮曾出现一次 1.642 秒采样空隙；补跑最大采样间隔为 54.85 ms，峰值仍为 2215.5 MiB。冷启动列包含新进程导入、加载与第一条短句，磁盘及编译缓存没有清空，不能称为首次安装启动。空闲列取最后一条短句后约 1 秒的稳定值，本轮没有用 30 秒空闲或数小时驻留替代它。

从原版 FP32 直接换到 FP16 低显存档，峰值下降约 80.7%；换到极限档下降约 87.3%。这同时包含执行架构、参考预处理、精度、分块和生命周期的变化，不能都算成 FP16 本身的收益。当前 SakuraTTS FP32 到 FP16 低显存档为 2049.1 → 723.0 MiB，下降约 64.7%，同样是组合配置收益。

## 本轮省下的显存来自哪里

现有双 FP16 分块配置已经能达到 865 MiB。此次最有效的推进是把已存在的生命周期能力组合起来，并按统一口径验证：

- `release-state` 在语义生成结束后释放 KV、CUDA Graph 和请求工作区。完整峰值再少 **142 MiB**，请求后空闲少 **220 MiB**。
- `staged` 继续在声学执行前关闭 GPT，再加载声学模型；片段完成后关闭声学 worker。相对 `release-state`，完整峰值再少 **248 MiB**，空闲降到约 **101.5 MiB**。

这些是完整进程计数的实测差值，包含池缓存和运行库影响，不能逐项归因于某一张量。关闭模型后，仍存活的主进程保留部分驱动或运行库分配，所以空闲不是零；本轮所有自有测量进程最终都已退出。

三种 FP16 生命周期策略使用同一模型包、精度、块长和 capacity=2048。各组对应的 **12 对 PCM 全部逐位相同**，语义 token 与停止结果也一致。由常驻改成释放状态、再改成分阶段加载，没有在这组样本上引入额外音频差异。

本轮没有缩短生成上限、裁掉文本或降低 KV 容量来压低数字，也没有加入新的 INT8/INT4 量化。FP16 声学包已经通过既有工程筛查，`allow_experimental_acoustic_fp16` 只是允许加载该包，不会把普通 FP32 包自动转换。

## 低显存的延迟代价

以下是持续显存采样期间的完整请求耗时中位数。短句排除冷启动后 n=3，其他类别 n=2；它们用于判断量级，不作为无采样干扰的正式性能排名。

| FP16 策略 | 短句，3.46 秒音频 | 长句，25.46 秒音频 | 扩展长句，34.06 秒音频 |
|---|---:|---:|---:|
| 常驻 | 0.213 s | 2.978 s | 4.255 s |
| 释放请求状态 | 0.223 s | 2.735 s | 4.190 s |
| 分阶段加载 | 3.074 s | 5.543 s | 6.920 s |

释放请求状态的额外成本在这组数据中较小；长句更快的差异不能据此认定为稳定加速。分阶段加载每次都重新读取、校验和上传权重，并重建声学 Session，约增加 2.7–2.9 秒等待。它适合显存优先的可选档，不适合直接替换低延迟默认档。这里没有单独验证流式首包延迟。

## 新增 Prefill 分块的结果

本轮新增了可选参数 `gpt_prefill_query_chunk_size`，默认仍为 `0`。设为 `128` 时，一次计算 128 行 query，每行仍读取全部 key，保留文本双向、文本不读取音频、音频因果的掩码。

scores 的存储规模由 `heads × N × N` 变成 `heads × min(128, N) × N`，mask 同样按行分块。KV 容量与生成规则没有改变。这解决长前缀的平方级临时矩阵，但不是完整推理的显存硬上限。

真实 GPU 固定历史验证结果如下：

- FP32：四类输入、1182 步 logits 与原路径逐位相同，三次重复、状态重建和 Graph/eager 对照通过。
- FP16：四类输入的 1182 步 argmax 全部相同，但长句和多句的 logits 未满足原严格容差，最大绝对差约 0.1048 和 0.0801。工程筛查通过不等于采样等价。
- 自然生成：长句从 629 变成 640 个语义 token，扩展长句从 844 变成 859 个；12 次请求中有 4 次对应 PCM 改变。分阶段配置的完整峰值仍是 475 MiB。

FP16 原路径的固定历史基线还出现一次多句 warm/repeat 非逐位相同，原始失败记录已保留，不能宣称分块修复了这个问题。GEMM 形状变化可能改变浮点累加顺序，但本轮没有内核追踪，不能把它写成已确定的原因。

因此，Prefill 分块保留为显式实验选项，**本次两档推荐配置都不启用它**。当前测试输入下，它没有继续降低完整峰值，却增加了数值与采样验证成本。

## 内容与音质检查

本轮用本地 `faster-whisper-large-v3-turbo`、CPU INT8、固定日文识别了 20 条 WAV。识别不使用目标文本提示、hotwords 或 VAD，也没有上传音频。样本覆盖当前 FP32、FP16 低显存档、FP16 query 分块候选，以及下面的分句方案。

短句、普通长句和多句的转录主体完整。需要保留两个问题：

1. `cut0` 不分句时，FP32、FP16 和 query 分块候选的扩展长句尾部都存在转写遗漏或异常。它不是只在 FP16 出现的新问题，但当前记录不能区分实际合成漏读与 ASR 误识。
2. 标点样本的末尾“ちゃんと言ってね”在多个配置中转写异常，仍需试听确认。

随后对同一 FP16 `release-state` 配置显式使用 `cut5` 按标点分句，另跑了 12 次请求：

| 分句补测 | 冷启动至首句峰值 | 全流程峰值 | 空闲 |
|---|---:|---:|---:|
| 双 FP16 + release-state + cut5 | 657.0 MiB | **665.0 MiB** | 543.0 MiB |

扩展长句的尾部内容这次均有对应转录；仅作诊断的 NFKC 去标点字符编辑距离由 27/159 降到 5/159。后者仍包含“おかえりなさい / お帰りなさい”等正字差异，不是实际读音错误率。标点例仍有疑点。分句会重置各片段的生成过程，改变停顿、输出长度和采样轨迹，因此没有用这组结果计算相对原版 `cut0` 的优化百分比。

这些结果支持优先验收“释放状态 + 正常分句”的低显存档。**本轮没有完成人工盲听，不能宣称 FP16 与 FP32 听感相同，也不能把请求成功或 ASR 转写当作音质通过。** 模型包的 `quality_accepted` 状态没有被改成通过。

## 复现本轮配置

本报告的两份原始配置后来按[四档方案](../../docs/inference-profiles.md)整理，复现时使用以下位置：

- [examples/fp16.json](../../examples/fp16.json)：原 `examples/low-vram.json` 对应的 C 档；双 FP16、chunk256、arena 回收、`release-state`，capacity=2048，声学 Session 常驻。
- [旧极限档研究配置](../experiments/configs/fp16-staged-resident-acoustics.json)：原 `examples/minimum-vram.json` 对应的 F 档；总体生命周期为 `staged`，声学 Session 仍同时驻留，仅供复现 475 MiB 历史数据。

两者都要求已经转换且筛查通过的 FP16 分块声学包。本机实际测试配置是 `outputs/low-vram-20260921/fp16.json`；它引用已有本地模型产物，普通源码克隆不会包含这些权重和参考音频。

在项目根目录，用低显存档合成并显式分句：

```powershell
.venv-windows-runtime/Scripts/python.exe -m sakuratts tts `
  outputs/low-vram-20260921/fp16.json `
  --experimental examples/fp16.json `
  --split-method cut5 --text "こんにちは。今日もよろしくね。" `
  --output outputs/low-vram-example.wav
```

需要复现本报告的旧极限档时，将实验选项文件改成 `research/experiments/configs/fp16-staged-resident-acoustics.json`。本报告 475 MiB 的实测使用 `cut0`；本轮没有测量 `staged + cut5` 的组合峰值或延迟。分阶段策略每个片段都重载模型，分句较多时尤其要注意等待时间。当前 `examples/minimum-vram.json` 对应后续 H 档，不能用本报告的数值描述它。

HTTP 可通过 `serve MODEL --experimental examples/fp16.json` 使用释放状态档；请求中的 `text_split_method` 另设为 `cut5`。当前 HTTP 包装层仍拒绝 `staged`，极限档使用公开 Python `Engine` 或 `tts` CLI。本轮完整峰值来自公开 `Engine`，没有单独对 HTTP 入口重新采集峰值。传统配置 `is_half: true` 的兼容限制也没有在本轮解除。

## “1G 以内”能承诺到哪里

1 GiB 是 1024 MiB，十进制 1 GB 约为 953.7 MiB。本轮 865、723、665、475 MiB 的候选都低于这两个数。FP32 默认路径仍高于 1 GiB。

计数与场景限制如下：

- WDDM 进程归属计数可能重复计入跨进程共享分配，不是独占物理 VRAM。`Shared Usage` 和 `Total Committed` 单独保存，没有混入 Dedicated 的表格。Shared 峰值原版约 78 MiB，原生双进程约 158 MiB；本轮未观察到它随长句大幅增加。
- 外部采样目标间隔为 20 ms。主要对照中位数约 20 ms、最大约 55–69 ms，极短尖峰仍可能漏采，因此全程使用“观测峰值”。原版 FP16 有缺口的首轮保留作复核，不作为主表依据。
- 原生路径使用预计算参考条件。首次处理陌生参考音频所需的转换/准备工具不包含在这些数字内，不能用本表承诺参考缓存未命中时也低于 1 GiB。
- vocoder 已分块，但 encoder/flow 仍处理整段上下文。更长文本、更长参考、其他模型、并发请求都可能提高峰值；本轮只有一个权重版本、五类文本、一个中性参考，没有验证物理 1 GB 显卡。
- 现有用户服务在资源测量时按授权暂停，测量结束后已按原命令恢复，`/health` 返回 `ready`、`model_loaded=true`。桌面和其他应用仍存在，整卡用量没有作为优化百分比的分母。

## 后续顺序

先把 665–723 MiB 档做成可重复安装、明确标注实验状态的低显存选项，并完成长句、标点、音色和分块接缝的盲听。补测真实低显存旧卡、参考缓存未命中、取消重试与长时间驻留后，再决定是否发布为正式低配版本。

475 MiB 档已表明错峰加载有较大空间。下一步应减少它每次约 3 秒的重载成本，例如保留 CPU 权重并按阶段上传、减少重复解析与 Session 构建；新增缓存时必须确认没有重新让两套 GPU 权重同时驻留。

继续追求更低峰值时，先在 475 MiB 档做声学内部阶段归因，再比较 latent/vocoder Session 错峰和重新筛查的 128 帧块。GPT W8/W4、KV 量化和 TensorRT/FP8 暂时后置：本轮 Prefill 分块已经说明，单个模块变小不一定降低完整峰值。当前没有新的量化实测，不能承诺再减固定的 MiB 数。
