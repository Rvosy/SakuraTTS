# 可选后台控制模式：首轮验证

日期：2026-09-22。环境：Windows / WDDM、RTX 5060，本机已有模型、编译和参考缓存。测试显式选择 FP16 标准档、声码器 chunk256、GPT capacity2048；产品默认仍为 FP32、`direct` 模式。

后续已完成[控制进程主存精简与 H 档 HTTP 接入](managed-refinement-20260922.md)。下文保留首轮数据及当时的能力边界；约 75 MB RSS 和 560 MB 私有提交均为系统内存指标。

首版 `managed` 已实现休眠启动、提前加载、合成自动唤醒、有限保活和空闲退出整棵推理进程树。默认模式的生命周期保持原状。接口见 [HTTP API](../../docs/http-api.md)，设计边界见 [后台驻留与提前唤醒](../../docs/background-runtime.md)。

## 实际验证

- 最终代码运行 `python -m unittest discover -s tests`：262 项通过，22.94 秒。包含默认入口与 HTTP 回归、17 项控制模式 HTTP 测试和 18 项真实子进程测试。
- 子进程测试覆盖加载及操作超时、管道写阻塞、取消、模型与参考设置恢复、父进程异常退出、工作进程异常退出后的子孙回收，以及跨 IPC 帧的原始音频片段边界。
- 真实模型验证休眠启动、显式唤醒、连续合成、手动休眠、原有 `/tts` 自动唤醒、流式输出、自动休眠和约 30 秒待机。手动及自动休眠后，推理进程和其子孙均已退出。测试服务最终正常退出，采样器无错误。
- 默认模式启动时加载模型，`/runtime` 返回 404。两种模式的 8 次同输入合成均得到相同的 221440 字节 PCM，SHA256 为 `365999ed967f98090b79cb3221d912a3eda4daa5edc1d71aca718f2af83509f5`。

真实输入为日文短句“おはよう。今日もよろしくね。”，固定参考、seed=1234、cut0。PCM 一致性覆盖本条输入，不能替代长句、陌生参考和音质验收。跨传输帧的片段边界由子进程测试验证；本轮 GPU 只测 WAV，未另跑 OGG / AAC 编码验收。

## 延迟

最终测量与单元测试分开运行，测量期间有外置显存及主存采样。首段时间从 HTTP 提交开始，到客户端读到 WAV 头后的首个 PCM 样本为止；202 响应和 WAV 头不计为音频。非流式必须完成整句后才返回，因此其首段与完整耗时接近。

| 场景 | managed | direct |
| --- | ---: | ---: |
| HTTP 就绪 | 1.011 s，模型未加载 | 4.069 s，模型已加载 |
| 显式唤醒至模型加载完成 | 3.547 s | 不适用 |
| 模型加载完成后的第一句，首段 / 完整 | 0.975 / 0.975 s | 0.983 / 0.983 s |
| 随后两句，首段 | 0.203、0.216 s | 0.235、0.244 s |
| 休眠中直接提交 `/tts`，首段 / 完整 | 4.416 / 4.417 s | 未测 |
| 已就绪时流式请求，首段 / 完整 | 0.237 / 0.237 s | 未测 |

第二次自动唤醒中的模型加载耗时为 3.453 秒。每种场景只有一到两个样本，不能据此计算 p95，也不能把本轮热请求差异解释为 `managed` 更快。

本轮 `wake` 提前完成了约 3.5 秒的模型加载，但第一句仍有约 1 秒开销。它没有执行真实推理预热；参考解析、首次前端与计算路径的耗时仍在请求中。后续应拆分测量这部分开销，再决定可选预热执行哪些步骤。尚未测量提前 0.5、1、2 秒发出提示的完整应用时序。

## 后台资源

统计整个自有 HTTP 进程树，包含本机 Python 启动器。内存使用十进制 MB，RSS 和私有提交分别记录；私有提交不等于当前驻留物理内存。采样请求间隔为 50 ms，实际还包含采样工作本身的耗时。

| 状态 | 进程树 RSS 中位数 | 进程树私有提交中位数 | Dedicated GPU | Shared GPU |
| --- | ---: | ---: | ---: | ---: |
| 刚启动、尚未唤醒 | 74.6 MB | 556.3 MB | 无对应进程计数实例 | 无对应进程计数实例 |
| 合成结束、等待空闲期限 | 2277.8 MB | 5701.9 MB | 569.4 MB | 165.7 MB |
| 推理进程退出后约 30 秒 | 74.7 MB | 559.6 MB | 无对应进程计数实例 | 无对应进程计数实例 |

休眠阶段有 475 个可用主存样本，覆盖 30.13 秒；保留进程的 CPU 时间增量在系统计时分辨率下为 0。末尾服务已退出、没有主存信息的一条采样被排除，未将缺失值填成零。该阶段包含观察结束时的状态检查和紧接着的服务退出过渡。

GPU 数值缺失保留为 `null`，不宣称读到了数值为零的显存计数。结合推理进程树已经退出，可以确认其进程资源已回收；控制服务仍保留约 75 MB RSS 和约 560 MB 私有提交，不能称为全部资源零占用。

本轮短句观测到的 Dedicated 峰值为 689.0 MB，Shared 峰值为 165.7 MB。它们只是本工作量和采样频率下的观测值，不能替代先前长短句混合基准，也不说明活动峰值比先前记录进一步下降。

## 复跑与记录

本机 GPU 验证命令：

```powershell
.venv\Scripts\python.exe outputs/managed-runtime-20260922/verify.py
C:\Python313\python.exe outputs/managed-runtime-20260922/summarize.py
```

验证脚本使用 `.venv-windows-runtime` 启动服务、随机空闲端口、现有 `outputs/windows-vocoder-public/runtime-fp16-chunk256.json` 和 `examples/fp16.json`，不重新转换资源。为了缩短测试，空闲超时设为 3 秒；产品默认仍为 60 秒。显式唤醒的保活设为 30 秒，随后用手动休眠提前结束。完整输入、启动参数与被测产品源码的 SHA256 保存在 `result.json`。

`outputs/managed-runtime-20260922/` 是本机忽略目录，包含验证脚本、`result.json`、`summary.json`、两份 `*-samples.json`、日志和 WAV。复跑依赖本机已有的模型及参考路径，这些资源不随 Git 分发。`initial-timeout-result.json` 保留首轮生产 worker 启动超时记录；该问题已通过调整 Windows NumPy 初始化与控制线程的先后顺序修复，并加入生产入口回归。`parallel-tests-result.json` 保留一次与测试并行的运行，未用于本文延迟表。

本轮没有完成 100 次睡醒、数小时挂机、其他机器、无编译缓存首次启动、陌生参考峰值或实际桌宠播放链路验收。总体 `policy="staged"` 仍不支持 HTTP；CPU 权重缓存和执行预热尚未加入。
